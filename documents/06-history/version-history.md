# 历史版本说明

本文按 Git 提交、历史标签和各阶段源码结构，整理项目从仓库创建到当前双分支架构的主要演进。版本说明关注功能范围、实现方式和关键决策，不把已经删除的类、接口或部署细节继续描述为现行能力。

## 版本编号说明

项目历史较长，曾出现过多轮发布编号。2026 年 10 月旧 Java 三模块架构已经使用过普通标签 `v5.1.1`，并继续发布到 `v5.3.1`；这些标签作为历史记录保留，不移动、不覆盖。

当前架构经过纯 Python 重建和 Web 只读化后，产品版本重新正式定义为 **V5.4.1**。为避免与旧标签冲突，并准确表达两个分支共同组成一个产品版本，当前基线使用分支作用域标签：

| 产品版本 | 分支 | 基线标签 | 含义 |
|---|---|---|---|
| V5.4.1 | `stock-trading` | `stock-trading/v5.4.1` | Python 数据、模型、交易和复盘权威实现 |
| V5.4.1 | `stock-web` | `stock-web/v5.4.1` | Java/React 只读控制台、文档工作台和展示能力 |

Python 包的 `0.1.x` 版本用于独立 Wheel 和生产发布节奏，不等同于产品架构版本。当前源码中的 Python 包版本为 `0.1.54`，产品基线仍统一称为 V5.4.1。

## 版本总览

| 阶段 | 主要时间 | 代表节点 | 核心定位 |
|---|---|---|---|
| V1 原型 | 2023-03 | 仓库创建 | 从基金交易管理概念开始验证项目方向 |
| V2 单体自动交易 | 2023-04 至 2024-04 | `v2.10.12` | Java 单体完成数据、模型、调度和券商交易闭环 |
| V3 前后端平台化 | 2024-05 至 2026-03 | `v3.1.10`、`v3.1.27` | 模型自动训练、前后端拆分和现代化工程升级 |
| V4 智能交易平台 | 2026-10 | `V4.9.5`、`V4.9.6` | 新闻、模型、Agent、任务和交易能力集中到 Java 平台 |
| V5 架构收口 | 2026-10 至 2026-11 | 旧 `v5.1.1` 至 `v5.3.1`、纯 Python 重建 | 从三模块平台转向 Python 交易权威与只读 Web 控制台 |
| V5.4.1 当前基线 | 2026-11-06 | 两个分支作用域标签 | 双分支职责固定，作为后续开发起点 |

## V1：项目原型与方向确认

仓库于 2023 年 3 月创建，最初 README 仅定义为“基金交易管理系统”。这一阶段主要完成项目命名、仓库和业务方向验证，尚未形成稳定的技术架构或可复用发布体系。

这一阶段留下的长期价值不是具体实现，而是两个基础目标：将行情、决策和交易记录纳入同一工程，以及让交易过程能够被程序化跟踪。

## V2：Java 单体自动交易系统

V2 将项目发展为可运行的 Java 自动交易系统。代表性版本 `v2.10.12` 使用 Java 8 和 Spring Boot 2.6.6，将行情处理、模型训练、定时调度、交易逻辑和管理接口放在同一个应用中。

主要功能：

- 对接证券平台，执行自动买卖和订单同步。
- 使用 Quartz 编排每日数据更新、模型训练和交易任务。
- 使用 DL4J/ND4J 构建 LSTM 模型，为 T+1 短线策略提供预测依据。
- 使用 MySQL、MongoDB 和 Redis 分别承担结构化业务数据、行情或模型数据、缓存与运行状态。
- 通过 GitHub Actions、Docker/Kubernetes 方向探索持续交付。

主要技术方式：Spring Boot 单体、MyBatis-Plus、MongoDB、Redis、Quartz、DL4J、Swagger。该方案功能集中、迭代直接，但数据、模型、调度和交易执行耦合较高，后续版本开始拆分职责。

## V3：前后端平台化与模型工程升级

V3 跨越了两个阶段。2024 年的 `v3.1.x` 增加价格预测、模型评分、归一化器序列化和自动触发训练任务；2026 年恢复建设后，工程升级为 Java 17、Spring Boot 3.2 和独立 React 前端。

主要功能：

- 模型从单一预测扩展到模型列表、评分、训练任务和结果展示。
- 后端继续承担数据同步、策略、交易和模型运行，前端提供独立管理界面。
- 增加模型制品管理、任务状态、运行日志和更完整的部署流程。
- CI 调整为 Runner 构建 JAR，再向服务器传输制品并构建镜像。

主要技术方式：后端模块与 `frontend-v2` 聚合，Java 17、Spring Boot 3.2.2、React、Vite、Ant Design、MySQL、MongoDB、Redis、DJL/PyTorch 和 TA4J。V3 确立了前后端分离和模型工程化方向，但交易、模型与平台能力仍集中在同一后端边界内。

## V4：智能交易平台与 Agent 能力

V4 在 2026 年 10 月快速扩展，代表节点为 `V4.9.5` 和 `V4.9.6`。这一阶段把行情、新闻、情绪、模型训练、预测、T+1 门禁、任务管理、交易记录和智能对话统一到一个产品中。

主要功能：

- 完善模型任务、预测批次、样本外评估和交易准入门禁。
- 建立新闻采集、情绪特征和模型数据就绪检查。
- 引入 Agent 对话、业务工具调用、运行审计和用户隔离。
- 建立更完整的交易日历、任务状态、模型制品和生产发布流程。

主要技术方式：Java 17、Spring Boot 3.2.10、React 19、MySQL、MongoDB、Redis、Flyway、Quartz、DJL/PyTorch、LangChain4j、Docker Compose 和标签驱动发布。V4 提升了平台完整性，但也使数据源、模型运行、Agent、调度和交易执行形成较大的共享系统。

## V5：从三模块平台到双分支架构

### 旧 V5 三模块阶段

2026 年 10 月 23 日至 27 日，项目把 Java 平台收敛为 `stock-backend`、`stock-agent`、`stock-frontend` 三个模块，并发布历史标签 `v5.1.1` 至 `v5.3.1`。这一阶段完成了 MySQL 权威状态、MongoDB 增量事实、Redis 会话缓存、独立 Agent 服务、模型镜像和分模块交付。

三模块方案解决了模块边界问题，但仍需要同时维护数据库迁移、模型原生依赖、Agent 服务、任务调度、交易执行和多镜像部署。后续重构选择进一步缩小生产主链，而不是继续增加平台组件。

### 纯 Python 交易主线

2026 年 10 月 30 日开始，`stock-trading` 分支重建为独立 Python 系统，数据、模型、排名、交易、订单结算和绩效复盘全部回归单一业务主线。

关键改造：

- BaoStock 采集行情，Parquet 保存分析数据，Qlib 生成 Alpha158 特征。
- LightGBM 生成完整横截面排名，交易规则收敛为 Rank5 买入和 Rank15 持仓轮换。
- SQLite 保存预测排名、交易计划、委托尝试、券商事实、已实现交易、模型状态和账户快照。
- Typer 提供独立 CLI；生产调度使用 Cron、配置文件、进程锁和日志轮转。
- 委托执行增加分阶段定价、轮询、撤单终态确认、失败恢复和重启幂等。
- Wheel 发布与业务数据分离，服务器运行目录、环境文件和数据同步入口统一。

这一决策正式确立：Python 是行情、模型、交易、绩效和任务状态的唯一权威实现。

### Web 只读控制台

`stock-web` 分支不再实现第二套交易后台，而是提供可选的只读控制台：

- Spring Boot 通过只读 SQLite 和 DuckDB JDBC 查询 Python 产生的 SQLite、Parquet 和模型结果。
- React 为 PC 和移动端维护独立组件树，展示概览、行情、交易、模型、日志和文档。
- 内置 Markdown 文档工作台和带来源引用的只读 Agent。
- 唯一写能力是受限 GitHub 开发 Agent，且与交易数据库、券商和 Python CLI 隔离。

该拆分减少了生产写入口，也使 Web 界面可以独立升级而不改变交易事实。

## V5.4.1 当前正式基线

自 2026 年 11 月 6 日起，当前产品正式定义为 **V5.4.1**，后续功能开发、问题修复和文档维护均以以下两条基线为起点：

1. `stock-trading/v5.4.1`：交易主线基线。
2. `stock-web/v5.4.1`：只读控制台基线。

当前基线的功能边界如下：

| 领域 | 权威实现 | 当前方式 |
|---|---|---|
| 行情与数据质量 | `stock-trading` | BaoStock、Parquet、缺失清单和统一质量阈值 |
| 特征、训练与排名 | `stock-trading` | Qlib Alpha158、LightGBM、完整横截面排名 |
| 交易与订单闭环 | `stock-trading` | T+1、先卖后买、券商事实同步、恢复与结算 |
| 绩效与模型复盘 | `stock-trading` | 已实现收益、月度复盘和模型状态判断 |
| 可视化与文档 | `stock-web` | Spring Boot 只读 API、React PC/移动端、Markdown 工作台 |
| 只读智能解释 | `stock-web` | 进程内会话、文档检索、行情/交易/模型/日志只读工具 |
| 生产调度与发布 | 两个分支独立维护 | Python Wheel/Cron；Web 容器和分支流水线 |

## 重要架构决策节点

| 时间 | 决策 | 原因与结果 |
|---|---|---|
| 2023-04 | 从概念仓库进入 Java 单体 | 快速打通数据、模型、调度和交易流程 |
| 2024-05 | 模型训练与评分任务化 | 让模型制品和运行结果可管理、可展示 |
| 2026-03 | 升级 Java 17、Spring Boot 3 和 React/Vite | 统一现代工程和前后端交付方式 |
| 2026-10 | 引入 DJL、新闻特征、Agent 和任务平台 | 扩展模型与智能解释能力，但系统复杂度明显增加 |
| 2026-10-23 | 拆分后端、Agent、前端三模块 | 明确服务职责和独立发布边界 |
| 2026-10-30 | 交易主线重建为纯 Python | 缩短数据到模型再到交易的技术链路，避免双重业务权威 |
| 2026-11-01 | Java 改为只读控制台 | 保留可视化价值，禁止控制台写入或修复交易状态 |
| 2026-11-03 | PC 与移动端组件树隔离 | 避免单一响应式页面互相牵制，分别优化交互 |
| 2026-11-06 | 建立 V5.4.1 双分支基线 | 固定 Python 权威与 Web 只读边界，作为后续版本起点 |

## 后续版本规则

- 产品版本同时覆盖 `stock-trading` 与 `stock-web`，发布说明必须写明两个分支各自的基线标签。
- Python 包版本可按独立发布节奏递增，但不得替代产品架构版本。
- 历史普通标签继续保留；禁止移动、删除或复用已有标签。
- 涉及业务权威、数据写入边界或交易入口的改变，必须同步更新架构决策和本章。
- 仅修改展示、文档或只读查询时，可以只发布 `stock-web`，但产品版本关系仍需可追溯。

具体历史取舍和已删除方向见[历史设计演进与保留结论](retained-design-evolution.md)。需要核对某个旧版本的类、接口或部署方式时，应直接查看对应标签和 Git 提交。
