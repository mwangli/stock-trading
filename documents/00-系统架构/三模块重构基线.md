# 三模块重构基线

## 目标

项目最终只保留三个 Maven 业务模块：

```text
stock-trading4/
├── stock-backend
├── stock-agent
└── stock-frontend
```

根 `pom.xml` 只负责依赖版本和模块聚合。`stock-backend`、`stock-agent`、`stock-frontend` 必须能够分别构建、发布和回滚，任一模块的构建不得隐式触发另外两个模块的构建。

## 当前规模

| 模块 | Java 文件数 | 约计代码行数 |
|---|---:|---:|
| `stock-base` | 6 | 168 |
| `stock-data` | 76 | 6,207 |
| `stock-model` | 92 | 10,836 |
| `stock-strategy` | 57 | 5,302 |
| `stock-trading` | 122 | 9,137 |

当前后端共 538 个 Java 文件、约 44,876 行代码。项目包含 46 个显式声明集合名的 MongoDB 文档和 88 处 `MongoRepository` 使用点，仅有一个模型单元测试。

## 当前依赖事实

```text
stock-base
  -> stock-data
  -> stock-model
  -> stock-strategy
  -> stock-trading
  -> stock-agent
  -> stock-job
  -> stock-starter

stock-web -> stock-starter
```

- `stock-agent` 直接调用数据、模型、策略、交易的 Service、Repository 和实体，尚不具备独立发布条件。
- `stock-job` 直接引用 Agent 调度协调类，Agent 不可用会影响统一调度模块的装配。
- `stock-starter` 同时预热后端模型和 Agent Embedding，启动职责混合。
- `stock-web` 通过 Maven 生命周期执行 Node 安装、`npm ci` 和前端构建，并被打入后端 JAR。
- 登录态由后端进程内 `HttpSession` 承载，无法直接跨独立 Agent 进程共享。
- 当前运行配置只接入 MongoDB，没有正式的 MySQL、Redis、JPA 和 Flyway 基线。

## 目标职责

### stock-backend

承载 `base`、`data`、`model`、`strategy`、`trading`、`job` 和启动装配。内部继续使用 `com.stock.<domain>` 包作为领域边界，但不再用 Maven 模块表达内部边界。

后端继续拥有市场事实采集、模型训练推理、确定性策略、交易风控、幂等、券商执行和统一 Quartz 调度权。

### stock-agent

承载 Agent Provider、AiServices、工具、RAG、Memory、会话、任务和受控交易判断。Agent 不直接依赖后端 Java 实现，不访问后端 Repository，不持有券商凭据，不直接写入真实订单。

Agent 通过受控内部 HTTP API 获取脱敏事实。后端通过内部 HTTP API 触发 Agent 影子判断与评估。

### stock-frontend

承载 React、Vite 和静态站点镜像。前端通过统一反向代理访问 Backend 和 Agent，不再作为 classpath 静态资源进入后端 JAR。

## 数据分层基线

### MySQL 权威业务数据

- 用户、用户偏好、系统运行配置和同步水位。
- Quartz 任务配置、任务执行记录和可中断状态。
- 策略配置、策略运行状态和模型版本激活关系。
- 模型元数据、训练运行、预测批次和训练快照元数据。
- 券商订单、成交记录、交易记录、同步批次和自动执行批次。
- Agent 会话、任务、交易计划、治理配置、API 预算和需要事务约束的状态。

### MongoDB 增量及大文档数据

- 日线、分钟线、新闻、公告、复权因子和每日可交易事实。
- 历史股票池、模型输入行情、预测明细、候选排名和回测明细。
- 账户与持仓历史快照、Agent 证据、工具调用审计、RAG 和向量文档。
- GridFS 中的模型参数和训练数据快照文件。

### Redis 可丢失缓存

- 跨服务登录 Session。
- 股票主数据、最新行情、交易日历、当前激活模型和运行配置缓存。
- Redis 故障不得改变订单、风控、任务、模型激活或交易计划的最终状态。

## 核心链路验收基线

| 链路 | 重构后必须保持的约束 |
|---|---|
| 登录 | 用户来源为 MySQL；Backend 与 Agent 能识别同一登录 Session |
| 行情同步 | 增量行情进入 MongoDB；同步水位进入 MySQL；空数据源不得伪装成功 |
| 模型预测 | 模型和批次元数据进入 MySQL；单股预测明细保留在 MongoDB |
| 选股策略 | Java 确定性策略仍为基线；Agent 只能单向收缩候选 |
| Agent 工具 | 只能调用后端受控只读 API，不能直接调用后端 Service 或 Repository |
| 真实交易 | Java 重新读取当前事实并执行权限、资金、持仓、交易日和幂等校验 |
| 定时任务 | 统一由 Backend 中的 Quartz 调度，不新增 `@Scheduled` |
| 前端构建 | Backend 和 Agent 构建均不得安装 Node 或执行 npm |

## 迁移纪律

1. 不保留旧模块、旧 API 映射、双写 Repository 或运行时兼容层。
2. 数据迁移采用停写、导出、转换、导入、核对、切换的离线方式。
3. 一次性迁移程序放入 `.tmp`，不得进入最终运行时代码。
4. 每个阶段只提交该阶段相关文件，现有用户未提交修改不得混入提交。
5. 源码静态检查、编译、测试、运行和生产验证分别记录，不互相替代。

## 分阶段验证入口

1. 结构阶段：POM 模块数、旧 artifactId、跨模块 import 和源码路径。
2. 存储阶段：Flyway 脚本、JPA/Mongo 扫描范围、集合与表的唯一约束。
3. 数据迁移阶段：记录数量、关键字段、唯一键、金额和状态分布核对。
4. Agent 阶段：禁止依赖后端实现、内部 API 契约和交易安全边界检查。
5. 前端阶段：独立构建配置、反向代理路径和后端 JAR 静态资源依赖检查。
6. 清理阶段：全仓搜索旧目录、旧模块、旧集合和冗余实现。
