## 4. 四种方案对比

### 4.1 方案 1：Java DJL 训练、加载和预测，发布 ONNX，移除 Python

#### 方案描述

Java 使用 DJL 定义模型、组织数据集、训练和评估，再将模型转换或导出为 ONNX；生产侧继续加载 ONNX 进行推理。

#### 优点

- 代码语言统一，Java 团队可在同一工程和调试体系内维护数据、训练和业务代码。
- 生产推理仍使用 ONNX，线上资源占用、跨平台能力和模型制品边界较清晰。
- 可以继续保留现有 ONNX 元数据、校验、Session 复用和故障关闭机制。
- 对结构固定、规模较小的 LSTM，DJL 能完成基本训练流程。

#### 缺点

- DJL 是 Java API 抽象，训练仍依赖具体原生引擎；移除 Python 不代表移除 PyTorch/MXNet 等原生依赖和版本兼容问题。
- DJL 的 ONNX Runtime Engine 主要用于加载和推理，不是通用的 Java 训练后 ONNX 导出器。自定义 DJL Block 到 ONNX 的稳定导出链路需要额外验证或自行维护转换逻辑。
- 训练模型与发布模型变成两种表示：DJL/引擎原始参数用于训练，ONNX 用于生产。仍需维护转换、算子支持和数值一致性测试。
- Transformer 微调、蒸馏、数据整理、指标分析和社区示例远少于 Python 的 PyTorch/Transformers 生态。
- 当前 Python 训练链路已经存在，改写为 Java 属于高成本迁移，且不会直接提升模型效果。

#### 自迭代适配度

中等。可以实现定时训练，但需要先补齐 Java 侧训练编排、检查点、超参数实验、ONNX 导出、预训练模型微调和评估工具。自迭代能力可做，但建设成本高，后续新模型接入速度慢。

#### 适用条件

- 团队明确禁止维护 Python。
- 模型长期限定为少量简单网络，不依赖快速变化的预训练模型生态。
- 已通过原型验证 DJL 训练模型能够稳定导出目标 ONNX，且所有算子、动态 Shape 和数值误差满足要求。

#### 结论

**不推荐作为当前项目主方案。** 它保留了 ONNX 的生产优势，但在训练端增加了转换链路和生态限制，达不到“更简洁”的实际目标。

### 4.2 方案 2：Java DJL 训练、加载和预测，使用原始模型，移除 Python

#### 方案描述

本文将“原始模型”定义为 DJL 所用训练引擎的原生模型或参数格式，例如 DJL 参数文件、PyTorch/TorchScript 等，不再转换为 ONNX。Java 同时承担训练和生产推理。

#### 优点

- 表面上的技术栈最统一：训练、加载、预测和业务编排都在 Java。
- 若训练和推理固定使用同一 DJL Engine，可减少 ONNX 导出失败或算子不支持问题。
- 简单自研网络可以直接保存参数并由相同 Java 模型结构加载。
- Java 类型、配置、日志、监控和部署流程可以统一。

#### 缺点

- 生产环境必须携带 DJL API、训练/推理 Engine 及对应原生库，包体、内存和平台兼容性通常比直接使用 ONNX Runtime 更复杂。
- “原始格式”容易与具体引擎绑定。更换引擎、升级 DJL 或跨语言复用时，迁移成本高于 ONNX。
- 若使用 DJL 参数文件，模型结构仍保存在 Java 代码中，制品本身不是完整、自描述、跨运行时的部署单元。
- 若使用 TorchScript 等格式，预训练模型准备和转换仍可能依赖 Python，无法保证真正移除 Python。
- 线上进程具备训练依赖和训练能力，职责边界容易重新混合；误触发训练、资源争抢和交易时段抖动的风险更高。
- 情感模型微调和新架构试验的效率明显弱于 Python 生态。

#### 自迭代适配度

中等偏低。技术上可以训练，但生产模型与 Java 代码、DJL 版本和 Engine 强耦合。模型升级经常需要同时升级应用，独立发布、灰度、回滚和跨版本兼容更难。

#### 适用条件

- 模型结构非常稳定且简单。
- 训练和推理都运行在受控的同一 Java 平台。
- 不要求跨语言、跨运行时或独立模型发布。
- 团队接受更重的 Java 原生深度学习运行环境。

#### 结论

**四个方案中最不适合当前场景。** 它实现了语言统一，但牺牲模型制品独立性、线上轻量性和后期微调效率。

### 4.3 方案 3：Python 训练，Java 加载 ONNX 并预测

#### 优点

- 与当前代码完全一致，不需要再次重写已经完成的训练和推理链路。
- Python/PyTorch/Transformers 适合模型实验、预训练模型微调、蒸馏、评估和数据分析。
- Java 线上只保留 ONNX Runtime，不需要 PyTorch 训练 Engine，也不需要常驻 Python。
- ONNX 是明确的发布契约，使训练实现与在线业务解耦；模型可以独立版本化、校验、灰度和回滚。
- Python 训练失败或本地训练节点离线，不影响 Java 继续使用最近一个已发布模型。
- 现有 SHA-256、指标门槛、兼容元数据、候选制品和 Session 复用都可以直接沿用。
- 后续更换训练框架时，只要仍输出相同 ONNX 契约，Java 在线代码无需跟随改写。

#### 缺点

- 需要维护 Java/Python 两套开发环境和少量跨语言数据契约。
- ONNX 导出可能遇到不支持算子、动态 Shape 或数值误差，需要保留 Golden Case 和双引擎校验。
- 特征计算若在两端重复实现，可能发生训练/预测偏差；必须以版本化快照和兼容元数据约束。
- 模型能力受 ONNX 可导出性约束，极少数动态模型或自定义算子可能需要改造。

#### 自迭代适配度

高。Python 可以快速接入新训练方法和预训练模型；Java 继续掌握数据截止点、模型激活和交易安全。只需在现有候选制品链路上增加调度、Champion/Challenger 评估和受控发布，即可形成闭环。

#### 结论

**当前最优方案。** 它不是折中，而是把训练生态和生产运行时分别放在更适合的位置。

### 4.4 方案 4：Python 训练和预测，作为常驻服务

#### 优点

- 训练与推理使用同一 Python 模型实现，通常不需要 ONNX 转换，减少转换误差和算子限制。
- 最容易使用最新 PyTorch/Transformers 模型、自定义算子、GPU 和动态推理逻辑。
- 模型服务可以独立扩缩容和独立发布，适合高吞吐、GPU 推理或多业务共享。
- 微调、在线实验、A/B 测试和多模型路由的扩展空间最大。

#### 缺点

- 增加一个常驻进程/容器、内部接口、序列化、超时、重试、熔断、鉴权、监控、日志关联和版本兼容。
- 2C4G 环境需要同时维持 JVM、Python、模型运行时和数据库，常驻内存与故障面明显增加。
- 每次预测增加进程间或网络调用，批量、超时和背压处理不当会影响交易链路。
- Python 服务不可用会直接阻断候选生成；必须额外设计健康检查、降级和故障恢复。
- 训练与在线预测如果共用服务资源，容易在训练期间影响预测稳定性；实际仍应拆分训练 Worker 和推理服务。
- 对当前单实例、低频交易规模而言，服务化收益不足以覆盖运维成本。

#### 自迭代适配度

很高，但风险也最高。它适合成熟的模型平台，不适合把“自动训练后立即替换在线模型”直接做进交易系统。即使采用该方案，也必须保留候选评估、人工/规则门禁、灰度和回滚。

#### 适用条件

- 出现 ONNX 无法承载的核心模型或自定义算子。
- 需要 GPU 常驻推理、动态 Batch 或多个业务共享模型服务。
- 推理吞吐量足以抵消服务化成本。
- 有独立资源和运维能力，可将训练 Worker 与在线推理服务隔离。

#### 结论

**当前不推荐，保留为未来升级路径。** 只有出现明确的 ONNX 能力瓶颈或独立模型平台需求时再采用。

## 7. 自我迭代与微调设计

### 7.1 原则

“自我迭代”应定义为**自动产生候选模型，受控评估和发布**，而不是模型在生产交易过程中直接修改自身权重。

禁止以下行为：

- 交易时段在生产节点自动训练。
- 新数据到达后立即覆盖当前生产模型。
- 只根据训练损失下降就激活模型。
- Python 训练任务直接修改生产 `current` 指针。
- 未经样本外评估就使用实盘结果反向训练并上线。

### 7.2 迭代闭环

```text
Java 累积真实数据与结果反馈
  -> 收盘后生成不可变训练快照
  -> Python 数据质量与漂移检查
  -> Python 增量训练或全量重训
  -> 时间外验证、Walk-forward、分层和压力评估
  -> 导出 ONNX 并对比 PyTorch/ONNX 输出
  -> 生成 Challenger 候选制品
  -> Java 在回放/影子模式执行兼容性验证
  -> Champion 与 Challenger 对比
  -> 达标后受控激活
  -> 监控生产表现，异常时原子回退
```

### 7.3 训练触发策略

| 触发类型 | 建议条件 |
|---|---|
| 定期触发 | LSTM 每周或每月评估是否重训；情感模型按月或季度评估 |
| 数据量触发 | 新增有效样本达到最小数量，且覆盖足够交易日/事件 |
| 漂移触发 | 特征分布、预测置信度或标签分布连续越过阈值 |
| 表现触发 | Champion 在滚动窗口的 Rank IC、收益、回撤或负面召回恶化 |
| 规则变更触发 | 特征、标签、Tokenizer、股票池或行业映射版本发生变化 |

触发只代表启动候选训练，不代表自动上线。

### 7.4 LSTM 迭代策略

- 默认优先“固定结构、更新数据、全量重训”，保持可比较性。
- 样本增量较小时，可以以上一版本为初始化权重微调，但必须与从头训练的基线对照。
- 评估至少包含 Rank IC、ICIR、Top-K 扣费收益、最大回撤、换手率、方向准确率和下行风险校准。
- 必须按行业、市值、市场阶段和时间窗口分层，避免总体指标掩盖局部退化。
- 模型结构、特征版本或标签版本变化时视为新主版本，不允许直接热替换旧版本。

### 7.5 情感模型微调策略

- 持续收集人工确认或事后校验的公告、处罚、退市风险、业绩、并购等金融文本标签。
- 对重复转载和同一事件分组后再划分训练/验证/测试集，避免数据泄漏。
- 优先进行小学习率领域微调；样本不足时使用冻结部分层、类别权重或蒸馏，不盲目全参数训练。
- 重点门槛不是总体准确率，而是负面召回、Macro-F1、概率校准、强负面事件触发和候选排序影响。
- 每次发布必须同时冻结 Tokenizer、标签顺序、最大长度和文本清洗版本。

### 7.6 Champion/Challenger 发布门禁

Challenger 至少同时满足以下条件才允许激活：

1. 数据快照完整、无未来数据泄漏，训练和验证时间窗口可追溯。
2. 核心指标达到绝对门槛，且相对当前 Champion 无不可接受退化。
3. PyTorch 与 ONNX Golden Output 误差在阈值内。

## 10. 风险与验证清单

| 风险 | 控制措施 |
|---|---|
| 训练/预测特征不一致 | Java 导出权威快照；特征版本写入制品；固定 Golden Case |
| ONNX 转换误差 | 同批输入比较 PyTorch 与 ONNX；设最大误差门槛 |
| 新模型离线好、实盘差 | Walk-forward、成本后收益、分层稳定性和影子回放 |
| 自动迭代过拟合近期行情 | 多窗口评估、Champion 对照、最小样本量和冷却期 |
| 情感负面事件漏判 | 负面召回硬门槛、专项事件集和概率校准 |
| 模型切换导致服务抖动 | 新 Session 先加载校验，再原子替换；保留旧版本 |
| 本地训练节点不可用 | Java 继续使用最近已发布模型，不影响在线交易 |
| 模型或数据不可追溯 | Run ID、Dataset ID、代码版本、摘要和指标随制品保存 |

## 11. 最终决策

采用方案 3，并将其固化为以下架构原则：

> Java 是唯一模型训练、推理、风控和交易运行时；DJL 提供 Java API，PyTorch Engine 提供执行能力，MongoDB 管理 LSTM 模型版本和小型参数。

该方案对当前项目最合适，原因按优先级排列如下：

1. 已由现有代码实现主要链路，不需要再次迁移和制造双轨实现。
2. 线上无需 Python 常驻，最符合 2C4G 的轻量和稳定目标。
3. Python 保留了 LSTM 实验和 Transformer 微调所需的成熟生态。
4. ONNX 让模型发布独立于训练语言，职责和回滚边界最清楚。
5. 自我迭代可以通过候选模型、Champion/Challenger 和受控激活实现，无需引入在线自训练或常驻模型服务。
