# Data 市场事实模块

## 模块定位

`com.stock.data` 是 Backend 的市场事实数据边界，负责股票资料、行情、新闻、复权因子、参考序列、历史股票池和每日可交易状态的采集、标准化、持久化与只读查询。

本模块提供事实，不负责模型推断、模型排名或真实交易执行。外部数据源为空、解析失败或覆盖范围不明确时必须明确失败，不能把不完整数据伪装为成功结果。

## 核心能力

| 能力 | 主要职责 |
|---|---|
| 股票资料 | 全量同步代码、名称、市场、行业、上市和退市信息 |
| 行情 | 日线增量、历史回补、分钟数据、覆盖统计和查询 |
| 工作日规则 | 统一按周一至周五计算任务日期，不维护节假日日历 |
| 模型数据基础 | 复权因子、参考指数、历史股票池和每日可交易事实 |
| 新闻 | 采集、标准化、去重、分类和事件事实沉淀 |
| 数据质量 | 区分缺失、过期、解析失败、来源不可用和覆盖不足 |

## 重点能力详细设计

### 1. 股票资料全量同步与退市治理

**设计目标**：使用一次外部全量快照完成股票资料对账，避免主循环逐条查询数据库，并防止将接口短暂漏数误判为退市。

处理流程：

1. `StockListSyncService` 先通过 `SecuritiesClient` 获取完整股票列表；响应为空直接失败。
2. `StockDataParser` 解析并按股票代码去重，代码为空的记录不进入同步计划。
3. 一次性读取数据库现有股票资料，按代码划分为更新、新增和数据库独有三组。
4. 更新组只覆盖外部源明确返回的字段，保留本地已有但本次缺失的信息。
5. 新增组仅对缺少上市日期的股票补查上市日期，再按固定批次写入。
6. 数据库独有组只有在名称、证券类别或市场说明中存在明确退市语义时，才调用关联清理服务；其余记录保留并计入忽略数。

关键结果包括外部总数、新增数、更新数、已清理退市数、忽略缺失数、失败数和耗时。写入成功后清理股票资料缓存，避免读取旧列表。

失败语义：外部列表为空、解析后无有效代码或批量持久化异常均不得返回“同步成功”；退市证据不足只记为忽略，不执行删除。

### 2. 统一日线采集与历史回补

**设计目标**：只保留一套日线采集和一个事实集合，消除逐股票重复请求、字段不一致和页面与模型数据分叉。

- `TushareDailyClient` 是唯一日线外部来源，来源标识固定为 `TUSHARE_DAILY`，数据契约版本固定为 `TUSHARE_DAILY_V1`。
- `stock_prices` 是唯一日线事实集合，以 `(code, date)` 作为业务唯一键，同时保存 OHLC、`preClosePrice`、成交量、成交额、单位、来源版本和写入时间。
- `DataSyncScheduler.syncDailyStockData` 每个交易日只请求一次全市场日线，再按当前股票代码集合过滤并批量幂等写入，不再为约 4,000 只股票分别发起请求。
- `DataSyncScheduler.backfillHistoricalStockData` 按交易日扫描目标历史窗口；每个日期一次全市场请求，写入相同的 `stock_prices` 集合。
- 页面 K 线、最新行情、预测评估、Agent 查询和 V6 训练统一读取 `stock_prices`。原 `model_stock_daily_bars` 重复集合和证券平台日线接口已经删除。
- `pre_close` 必须保留。连续价格计算使用当日 `preClosePrice` 与前一日原始收盘价识别除权除息跳变，不能用前一日 `close` 无条件替代。

历史回填采用完整目标窗口幂等重扫，避免仅依据“最新已落库日期”而遗漏更早区间。模型训练前置检查同时校验固定来源版本、股票覆盖率和最新交易日时效；旧数据即使覆盖率足够，也不能再被判定为就绪。

存量环境切换按以下顺序完成：先发布统一采集代码，再触发 `stockPriceHistoryBackfill` 填充 `stock_prices`，确认 `TUSHARE_DAILY/TUSHARE_DAILY_V1` 的最新日期、覆盖股票数和目标窗口完整性，最后再清理数据库中已废弃的 `model_stock_daily_bars` 集合及 `sync_state` 表。源码基线已删除旧对象，但不会在未授权情况下自动删除现有数据库数据。

### 3. 工作日规则

**设计目标**：用最少状态统一训练、预测、行情同步和交易任务的日期推进规则。

`TradingCalendarService` 是无状态日期工具，只把周一至周五视为交易日，并提供前一工作日、下一工作日和区间工作日计算。系统不保存 MongoDB 交易日历、不访问外部日历接口，也不维护日历同步任务。

法定节假日如果位于周一至周五，任务仍按计划触发。行情供应商无数据时由现有无数据、待回补或跳过语义自然收敛；真实交易仍由券商状态、交易时间、风控和幂等规则最终决定。

### 4. 新闻采集、标准化与事件事实

**设计目标**：同时保留原始证据和可计算的标准化事实，让情感模型与策略可以追溯输入来源。

在线处理由 `NewsCollectionPipelineService` 编排，主要步骤为内容清洗、来源与时间标准化、文档类型识别、角色分类、质量状态判断和管线版本记录。新闻原文、标题、摘要、来源、发布时间和内容哈希属于基础事实；情感标签和事件分类属于派生结果，不能覆盖原始证据。

`NewsEventFactService` 将符合条件的文档转换为事件事实，并使用稳定标识抑制重复事件。重复文档、忽略文档和质量不足文档分别计数，不能统一当作成功事件。

历史治理由 `NewsCollectionBackfillService` 完成：

- 以管线版本作为回填状态主键。
- 按 MongoDB `_id` 升序游标分批读取，仅处理管线版本过期或质量状态未就绪的数据。
- 每批先运行与在线路径相同的处理管线，再保存新闻和事件事实。
- 每个成功批次持久化最后处理 ID、累计计数和类型分布。
- 达到单次最大处理量后回到 `PENDING`，下次从已保存游标继续。
- 发生异常时标记 `FAILED` 并保留最后成功游标，禁止从头重复回填。

新闻业务数据同时受月度 `globalDataCleanup` 兜底治理：原始 `stock_news` 默认保留 365 天，规范事件事实和日级新闻特征快照默认保留 730 天。该任务按发布时间或特征交易日执行服务端批量删除，不依赖某只股票再次采集才触发清理；当前回填状态、路由状态和未到终态的影子评估记录不在清理范围内。

### 5. 模型数据基础与跨模块查询

复权因子、参考指数、历史股票池、每日可交易状态和标准行情共同构成模型与回测的数据基础。`MarketDataFoundationService` 负责这些事实的导入或维护，数据必须携带业务日期、来源和版本信息。

`MarketDataQueryService` 是跨模块只读入口：

- 将内部 Entity 转换为稳定 DTO。
- 提供按股票、日期、时间窗口和信息截止时间查询的能力。
- 通过 `auditModelTrainingData` 一次性返回指定来源版本下模型日线、复权、历史股票池、可交易事实及市场/行业参考序列的结构化覆盖报告。
- 对缺失、覆盖不足和数据过期返回明确结果，不伪造补零数据。
- `model`、`decision`、`execution` 和 `platform` 只能通过公开 Service/DTO 读取市场事实。

### 6. 数据质量审计

`BacktestDataAuditService` 等质量服务在数据进入训练、回测或决策前检查覆盖范围、时间连续性、股票池有效性和关键信息缺失。质量结果至少区分：

| 状态 | 含义 | 处理要求 |
|---|---|---|
| 缺失 | 目标事实不存在 | 阻断依赖该事实的计算或明确跳过 |
| 过期 | 数据存在但不满足时效 | 不得作为实时交易依据 |
| 解析失败 | 已取得响应但无法形成可信记录 | 记录来源和解析错误并失败 |
| 来源不可用 | 外部服务不可达或拒绝请求 | 保留原有事实，不写入空结果 |
| 覆盖不足 | 有部分数据但未达到业务门槛 | 返回覆盖率和缺口，不伪装完整 |

审计只判断数据是否满足用途，不在本模块内执行模型训练、策略评分或交易放行。

模型训练前置检查只允许自动调用已有可靠来源的幂等回填。统一日线由 Tushare 按日期准备到 `stock_prices`，新闻日级特征快照具备持久化游标回填；复权因子、历史行业和参考序列仍以外部导入事实为准，缺失时返回缺口并由训练运行进入 `WAITING_DATA`，禁止从当前股票资料推测历史值。训练可复现性由包含来源版本、日期范围、样本键和标准化参数的不可变训练快照保证，不通过复制第二份永久日线集合实现。

## 数据与对外边界

- 市场 Repository 和 Entity 只在本模块内部使用。
- `MarketDataQueryService` 将市场持久化对象转换为明确 DTO，供 `model`、`strategy`、`trading` 和 `platform` 读取。
- 上游模块不得直接引用 `com.stock.data.repository` 或 `com.stock.data.entity`。
- Agent 只能通过 `stock-platform` 公开 Service 获取最小、只读、脱敏摘要。
- Caffeine 仅用于单进程可重建缓存，权威事实仍以持久化数据为准。

## 维护规则

- 新数据源接入优先归入 `client`、`parser` 和 `validator`，禁止恢复笼统 `support` 包。
- 跨模块输出必须使用 DTO，不暴露 Entity、Repository、MongoTemplate 或外部供应商响应对象。
- 日常增量、历史回补和数据修复保持独立状态，避免单个历史缺口阻断当日数据。
- 修改股票、行情、日历或新闻契约时，必须检查模型、决策、执行、调度和 Agent 查询 Service 的调用方。

## 专项设计：NewsCollectionQuality-v1

- 状态：`SOURCE_IMPLEMENTED`
- 最后核对日期：2026-10-29
- 当前证据：已完成生产历史治理、每日增量采集、失败重采、日期水位准备和最终审计
- 未验证边界：尚未完成固定人工标注集、重大风险召回与误报评估，以及新闻与行情日期对齐后的模型消融

### 目标与非目标

本专项将新闻质量治理前移到采集层。证券数据源返回的每条文档必须在持久化阶段完成原始内容留存、规范化、文档类型识别、业务角色识别、内容去重和事件事实同步。情感模型、选股和后续时序模型只消费版本化事件事实，不再各自清洗原始新闻。

本方案不删除原始文档，不把证券平台菜单编号直接解释为真实文档类型，不在数据治理阶段自动激活模型，也不承诺清洗一定改善收益。模型升级必须等待本专项的数据 Gate 取得运行证据。

### 当前数据证据

2026-10-23 对 `stock_news` 进行只读抽样时，集合约有 51.09 万条记录，其中约 97.67% 缺少完整事件元数据。来源高度集中，栏目“新闻”中大量记录实为交易所公告，栏目“公告”中又包含评级和行业研究内容。2,400 条标题样本的规范化重复率约为 16.08%。

历史 `stockRanking` 样本中的旧 `sentimentScore` 均值约为 0.99812，标准差约为 0.000861，不能证明新闻因子提供了有效横截面区分。当前源码虽已过滤非 `actionable` 结果，但新逻辑尚无回填、训练或实际选股评估证据。

### 采集链路与类职责

```text
证券数据源
  → 原始响应解析
  → 标题和正文规范化
  → 文档类型识别
  → 业务角色识别
  → 内容摘要与规范事件标识生成
  → stock_news 原始文档写入
  → stock_news_event_facts 幂等聚合
```

- `StockNewsDocumentFactory` 只负责请求详情并构造原始文档。
- `NewsDocumentNormalizer` 负责 HTML、URL、重复股票前缀、页眉页脚、免责声明和空白规范化。
- `NewsDocumentClassifier` 根据来源、标题和正文推导文档类型，不依赖菜单显示名称。
- `NewsDocumentRoleResolver` 将文档划分为 `TRADE_SIGNAL`、`RISK_ONLY`、`CONTEXT_ONLY` 或 `IGNORE`。
- `NewsCanonicalEventResolver` 生成规范化内容摘要和跨来源事件标识。
- `NewsCollectionPipelineService` 统一编排规则并写回治理字段。
- `NewsEventFactService` 将非 `IGNORE` 文档幂等聚合到事件事实集合。

### `stock_news` 原始文档契约

`stock_news` 保留原有 `title` 和 `content`，并维护以下治理字段：

| 字段 | 含义 |
|---|---|
| `rawMenuId` | 供应商菜单编号，仅用于来源追踪 |
| `rawTitle` / `rawContent` | 供应商原始标题和正文 |
| `normalizedTitle` / `normalizedContent` | 采集层规范化结果 |
| `sourceChannel` | 原始渠道名称，不承担业务类型语义 |
| `documentType` | 真实文档类型 |
| `documentRole` | 下游业务角色 |
| `contentHash` | 规范化标题和正文摘要 |
| `canonicalEventId` | 规范事件标识 |
| `noveltyScore` | 新颖度，范围 `[0,1]` |
| `materialityScore` | 重要性，范围 `[0,1]` |
| `stockSpecificity` | 股票相关度，范围 `[0,1]` |
| `pipelineVersion` | 采集治理规则版本 |
| `qualityStatus` / `qualityReason` | 质量状态和原因 |

菜单编号只写入 `rawMenuId`。既有 `category` 作为兼容展示字段保留，不再作为公告半衰期、模型权重或真实文档类型依据。

### 文档类型与业务角色

文档类型固定为 `OFFICIAL_DISCLOSURE`、`MEDIA_NEWS`、`RESEARCH_REPORT`、`RATING_CHANGE`、`INVESTOR_QA` 和 `UNKNOWN`。

| 业务角色 | 下游用途 |
|---|---|
| `TRADE_SIGNAL` | 可进入情感推理和模型特征 |
| `RISK_ONLY` | 进入 Java 风险门禁，不与正向 Alpha 抵消 |
| `CONTEXT_ONLY` | 保留研究和审计，不参与选股评分 |
| `IGNORE` | 空内容、模板噪声或无有效语义，不生成事件事实 |

董事会和监事会例行决议、制度修订、独立董事声明等默认属于 `CONTEXT_ONLY`。只有包含明确增减持、回购、控制权变化、重大合同、业绩变化、监管处罚或诉讼事实时，才能提升为可交易角色。

### `stock_news_event_facts` 事件事实契约

交易事件事实以 `(stockCode, canonicalEventId)` 唯一，仅保存 `TRADE_SIGNAL` 和 `RISK_ONLY` 的规范化文本、文档类型、业务角色、事件类型、发布时间、来源集合、外部文档标识集合、重要性和采集管线版本。`CONTEXT_ONLY` 保留在原始新闻治理字段中供研究查询，不再向交易事件事实集合重复保存完整正文。

重复文档只补充来源和外部标识，不重复形成情感权重。事件事实保留最早发布时间和最晚观察时间，历史乱序回填不能覆盖点时边界。相同 `canonicalEventId` 可以关联不同股票，但每只股票保留独立事实。

情感训练和新闻排名只消费 `TRADE_SIGNAL`；`RISK_ONLY` 只进入独立 Java 风险门禁；`CONTEXT_ONLY` 不生成交易事件事实。没有事件事实与存在中性事件必须分别表达，不能统一编码为固定 `0.5`。`NEWS_EVENT_RANKING_ENABLED` 与 `NEWS_EVENT_RISK_GATE_ENABLED` 默认均为 `false`，对应收益 Gate 或风险 Gate 取得证据后才能分别开启。

### 历史回填设计

历史回填复用 `NewsCollectionPipelineService`，通过 MongoDB `_id` 游标升序处理，并持久化 `pipelineVersion`、最后游标、扫描数、更新数、新增事实数、重复数、文档类型分布、业务角色分布、忽略数和失败数。

只有一批原始文档和对应事件事实都持久化成功后才能推进游标。达到单次最大处理量后状态回到 `PENDING`，下次从已保存游标继续；异常时标记 `FAILED` 并保留最后成功游标。

任务通过 `JobConfig + JobSchedulerService` 注册且默认暂停，防止未完成容量验证时在 2C4G 节点自动扫描约 51 万条文档，不新增 `@Scheduled`。

### `NEWS_COLLECTION_V5` 规则与验证

2026-10-24 对 `stock_news` 执行两阶段验证：先按 `_id` 读取最早和最新各 1,200 条进行只读规则迭代，再对最早和最新各 5,000 条执行隔离影子回填。生产 `stock_news` 和生产 `stock_news_event_facts` 均未修改。

V1 至 V3 完成 HTML、URL、重复前缀和免责声明清理，纠正菜单栏目与真实文档类型错位，并加入例行公告、行情播报和硬风险分流。V3 的 2,400 条抽样结果为 `RISK_ONLY` 8 条、`TRADE_SIGNAL` 380 条、`CONTEXT_ONLY` 1,896 条、`IGNORE` 116 条。

V4/V5 继续完成以下收敛：

- 标题当前事实优先于正文历史描述，避免长正文中的解除、否定或模板语义覆盖当前风险事件。
- 业绩预盈、预亏、预增、预减，中标候选，股票质押式回购，以及诉讼仲裁进展加入明确标题规则。
- 解除司法冻结、解除冻结、解冻和解除质押优先作为解除事件；同时包含新增、补充、轮候或再次质押时仍按当前风险处理。

- 事件事实只保存 `TRADE_SIGNAL` 和 `RISK_ONLY`；`CONTEXT_ONLY` 只保留治理元数据和原始文档引用。
- 同批事件先聚合后无序 bulk upsert，并保留 `observedDocumentRoles` 供跨来源审计。

### 可靠清洗流水线设计

生产清洗采用“可重放原始事实 + 确定性治理 + 事件事实幂等聚合 + 游标最后提交”的补偿事务模型，不依赖 MongoDB 跨集合事务。单批处理顺序固定为：

```text
只读加载原始文档
  → 内存执行 NEWS_COLLECTION_V5
  → stock_news 写入治理字段并保持 FACT_PENDING
  → stock_news_event_facts 按 (stockCode, canonicalEventId) 幂等 upsert
  → 原始文档标记 READY
  → 保存批次统计和 lastProcessedId
```

任何步骤失败都不得推进游标。原始文档已保存但事件事实失败时，文档保留 `FACT_PENDING`，在线外部采集和历史回填都必须优先重试该状态；重复执行通过确定性文档 ID、`contentHash`、`canonicalEventId` 和 `$addToSet` 保证不重复增加事件权重。

可靠性边界固定如下：

1. **输入校验**：缺少来源、标题、股票代码或发布时间的文档不得直接进入事件事实；可修复字段进入待重试，不可修复文档标记 `INVALID` 并保存原因。
2. **单一规则源**：在线采集、历史回填和影子验证必须调用相同的规范化、分类、角色和事件标识组件，禁止维护第二套脚本规则。
3. **失败恢复**：任务启动时先扫描当前版本的 `FACT_PENDING`；即使版本状态已经是 `COMPLETED`，仍需检查残留待同步文档和新导入旧版本文档，不能直接无条件返回。
4. **毒性文档隔离**：同一文档连续失败达到阈值后从正常批次隔离，记录文档 ID、规则版本、失败阶段、错误摘要和重试次数；不得因单条坏数据永久阻塞整个游标。
5. **并发控制**：Quartz 使用 `@DisallowConcurrentExecution`，在线采集和历史回填通过确定性 upsert 协同；同一 `pipelineVersion` 只允许一个历史回填执行实例。
6. **版本升级**：新规则版本先写影子集合并通过数据 Gate，再建立独立版本游标执行生产回填。旧版本状态和原始内容继续保留，禁止原地覆盖后失去审计能力。
7. **点时一致性**：事件事实保留原始发布时间、首次观察时间和最后观察时间；训练与选股只能读取截止时间之前已发布且已入库的事实。
8. **资源控制**：批次默认 500 条，单次任务最多 50,000 条；运行前检查 MongoDB 可写、剩余磁盘和集合水位，磁盘使用率达到 70% 告警、80% 时停止新增影子回填。
9. **可观测性**：每批记录扫描、规范化、事件候选、唯一事件、重复、忽略、失败、耗时、游标和存储增量；报告不得记录密码、完整连接串或未经脱敏的正文。
10. **下游隔离**：只有 `READY + TRADE_SIGNAL` 才能进入情感与时序特征，只有 `READY + RISK_ONLY` 才能进入风险门禁，`FACT_PENDING`、`INVALID` 和 `CONTEXT_ONLY` 不进入交易评分。

完成态任务的残留工作探测和连续失败文档的隔离重试已落地，并通过本轮生产全量治理与定向重采验证。无人值守运行仍必须保留单实例控制、失败游标、毒性文档隔离和默认暂停的大规模历史任务边界。

### 数据 Gate

- 新采集数据治理字段完整率不低于 99.5%。
- 固定标注集文档类型准确率不低于 90%。
- 重大风险事件召回率不低于 95%，误报率不高于 5%。
- 规范化后的未合并重复事件率不高于 5%。
- 模型输入可追溯到原始文档、事件事实和 `pipelineVersion`。
- 点时查询不读取选股截止时刻之后发布或入库的事实。
- 完成无新闻、原始新闻和事件事实三组 Walk-Forward 消融比较。
- 事件事实方案在多数测试窗口产生正向 Rank IC，且扣成本 Top 10% 收益不低于无新闻基线。

若收益类 Gate 未通过，新闻排名权重保持为 `0`；风险事件门禁可以在风险召回和误报 Gate 独立通过后继续使用。

### 影响边界与退出条件

- `market` 负责采集治理、原始文档和事件事实。
- `model` 只消费已治理事实，不维护第二套文本清洗规则。
- `decision` 只消费点时有效的事实聚合和风险门禁结果。
- `execution` 继续负责权限、资金、持仓、幂等、风控和券商执行。

源码验收已覆盖规范化、文档分类、角色分类、规范事件标识、重复事实合并、回填游标、任务注册、下游事实读取以及排名/风险独立开关。2026-10-28 至 2026-10-29 已取得 MongoDB 历史治理、增量采集、日期水位和最终审计的运行证据；自动化测试、固定人工标注质量和模型收益消融仍未完成。

## 专项设计：TemporalNewsFeature-v2

### 事实输入契约

`temporal-news-v2-8d` 只消费规范化的 `stock_news_event_facts`，要求股票代码、规范标题或正文、发布时间、业务角色、事件类型、来源、重要性、新颖度、个股相关度和 `pipelineVersion` 可追溯。情感模型必须读取同一事件事实，并使用同一标题优先、关键句和最多三块的输入组装规则。

所有快照都绑定 `featureTradeDate` 和 `cutoffTime`。事件发布时间晚于截止时间、标签依赖未来收益、后验人工结论或目标交易日之后信息时，禁止进入特征。长文本不能直接从头截断；标题必须保留，正文优先选择财务、监管、风险、否定和反转关键句，再补充普通句，最多三块。

### 角色隔离与日级快照

- `TRADE_SIGNAL` 才能进入固定 8 维紧凑新闻快照。
- `RISK_ONLY` 不参与情感正负抵消、不进入 Ranking LSTM 或 MASTER 普通特征，继续由 Java 风险门禁独立消费。
- `news_feature_snapshots` 只持久化 5 日点时窗口内存在合格事件的股票日 8D 聚合；按股票、交易日、行情来源版本和特征版本唯一，保存情感模型版本、采集管线版本、截止时间、输入事件数和最晚发布时间。
- `news_feature_completeness` 按行情来源、版本、特征版本和交易日保存 `COMPLETE` 水位。某样本键没有稀疏快照且日期水位完整时，训练内存中解释为合法 `NO_EVENT`；日期水位缺失或失败时解释为 `UNAVAILABLE` 并阻断。
- 训练和推理按入选样本范围批量读取稀疏快照并在内存关联，不持久化全市场全零文档，不在样本循环内在线推理新闻或逐条查询 MongoDB。

2026-10-29 最终运行 `db14d55f-2c4c-4af8-a4f8-c030960916cc` 删除了 1,721 条旧式全零 `NO_EVENT` 文档。最终审计覆盖 432 个预期日期，432 个日期均为 `COMPLETE`，完成率 100%；既有 V6.1 快照区间内有事件稀疏快照为 0，契约非法、前视和来源追溯缺失均为 0，`passed=true`。稀疏快照为 0 的原因是新闻始于 2023-10-09，而该不可变训练快照止于 2023-09-18，不是审计漏数，也不代表统一日线库仍停留在该日期。

### 标注与质量门禁

人工金标至少覆盖正面、中性、负面、否定、反转、长文本、公告、监管和新闻来源，并按规范事件分组切分训练、验证和测试，避免同一事件改写泄漏到不同集合。弱标注必须保存规则版本、来源和置信度，只能用于预训练或样本扩充。新闻采集覆盖率、发布时间完整率、去重质量和角色准确率未通过前，不得把模型加载成功描述为特征质量通过。
### 原始新闻与磁盘保留策略

原始文档和事件事实采用独立生命周期。`StockNewsService` 的 365 天与单股 300 条限制只清理 `stock_news`，不得再删除 `stock_news_event_facts`；事件事实至少保留到对应 `temporal-news-v2-8d` 快照、点时审计和三组 Walk-Forward 消融全部完成。生产清理顺序固定为：先完成 V5 全量治理，再完成日期水位与稀疏快照审计，再确认消融结果，最后按角色压缩原始正文。

- `TRADE_SIGNAL`、`RISK_ONLY`：保留事件事实、来源集合、规范文本、版本和情感结果；原文在审计窗口结束后可转冷存储。
- `CONTEXT_ONLY`：快照与规则验证完成后仅保留标题、URL、哈希、来源、时间、角色和管线版本，正文可清除。
- `IGNORE`：仅保留短期审计元数据，正文优先清除。
- 同一 `canonicalEventId` 的转载：事件事实保留一份规范正文，其余来源只保留 provenance。
- `news_feature_snapshots`：仅长期保留存在合格事件的固定 8 维稀疏向量；无事件语义由日期完备性水位表达，不受原始新闻清理周期影响。

MongoDB 删除正文或文档只会形成可复用空间，通常不会立即缩小磁盘文件。磁盘使用达到 70% 时停止扩充原始正文并优先生成快照；达到 80% 时停止非必要采集。需要向操作系统归还空间时，必须在备份和维护窗口内执行集合重写、受控 `compact` 或 dump/restore，不能在生产高峰直接操作。
