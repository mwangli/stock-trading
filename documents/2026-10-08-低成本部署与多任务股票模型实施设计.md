# 低成本部署与多任务股票模型实施设计

## 1. 文档信息

| 项目 | 内容 |
|---|---|
| 日期 | 2026-10-08 |
| 目标 | 在可控成本下长期稳定运行真实交易系统，并实现共享模型的个股/行业差异表达与多任务输出 |
| 在线原则 | 交易时段只推理，不在生产云主机训练模型 |
| 安全原则 | Agent 不直接访问券商，不绕过 Java 风控、幂等和真实写入门禁 |

## 2. 部署方案结论

### 2.1 方案 A：2C4G 云服务器

原始 Docker 配置不能直接在 4GB 内存内稳定运行。旧生产配置为后端、MySQL、MongoDB、浏览器分别预留 4GB、2GB、2GB、2GB，资源预算已经超过物理内存。浏览器容器已从常驻部署中删除，券商侧改为 HTTP 登录和进程内短期 Token。百度云 OCR 的 50 张唯一验证码验证仅达到 52% 单路径准确率，未达到 85% 目标，因此自动提交默认关闭；生产登录仍需专用验证码模型或人工兜底。

调整后，2C4G 可承担以下在线职责：

- Nginx/React 静态页面。
- Spring Boot API、调度、确定性策略、风控和券商接口。
- MySQL、MongoDB 的轻量单机实例。
- 已训练共享模型的 CPU 推理。
- 定时备份和监控，但不执行 LSTM、情感模型或大语言模型训练。

建议内存预算：

| 组件 | 建议上限 |
|---|---:|
| 操作系统和 Docker | 600-800MB |
| Spring Boot + 模型推理（迁移期 DJL，目标 ONNX） | 1200-1500MB |
| MySQL | 450-600MB |
| MongoDB | 550-700MB |

| Web/Nginx | 64-96MB |
| 峰值缓冲 | 300-500MB |

4GB 只能作为轻负载下限，要求限制 JVM 堆、数据库缓存、日志文件和批量查询规模。若同时进行全市场批量特征构建、大量历史同步或专用验证码模型推理，仍可能出现内存和 CPU 抖动。长期线上规格优先 4C8G；2C4G 更适合初期低频真实交易和灾备节点。

按 2026-10-08 常见促销与续费差异做预算，不作为供应商报价：2C4G 云主机通常约 600-1800 元/年，系统盘、快照、对象存储、流量和短信等另计。应以购买当日、地域、带宽和续费价格复核，不能只看首年促销价。

### 2.2 方案 B：16GB 本地小型服务器

16GB 本地服务器可以稳定运行当前 Java、MySQL、MongoDB 和离线 LSTM 训练，也可以运行 3B/4B 量化模型的 Ollama。运行 7B/8B 量化模型时仍可用，但与数据库、训练任务并发后内存余量有限，CPU 推理速度也取决于处理器和内存带宽。

采购预算建议按 1200-2500 元一次性投入估算，另加硬盘、UPS 和备份盘。10-30W 的常年功耗约为 88-263kWh/年，电费通常远低于云主机年费，但本地方案需要自行承担断电、宽带中断、动态公网地址、硬盘故障和远程维护风险。

若后续明确运行 7B/8B Ollama、Agent、向量库并保留模型训练能力，建议直接选择 32GB 内存和可扩展 NVMe；16GB 是可运行下限，不是长期舒适规格。

### 2.3 推荐长期架构：云端在线 + 本地离线的混合部署

推荐把两个方案组合，而不是二选一：

1. 2C4G 云主机仅运行在线交易闭环、数据库和模型推理，删除浏览器容器并禁止在线训练。
2. 16GB/32GB 本地服务器执行收盘后数据准备、LSTM 训练、回测、Ollama 和 Agent 分析。
3. 本地训练产物必须包含模型版本、特征版本、标签版本、词表/哈希桶参数、样本时间范围和指标摘要。
4. 只有通过样本外门槛的模型才发布到云端；云端先校验元数据和文件摘要，再原子切换当前模型。
5. 云端保留上一版本以便快速回退。本地和云端数据库通过加密备份同步，不做双主写入。
6. Agent 只输出结构化建议或 `TradePlan`，最终交易仍由 Java 重新取价、重新风控并调用券商适配器。

该架构兼顾在线稳定性、训练资源弹性和长期成本。若本地断电，云端继续使用最近一个已发布模型，不影响交易时段推理。

## 3. 模型训练与发布方式

采用“本地离线训练、线上只预测”方案：

- 收盘后在本地读取截至当日可获得的数据，生成 Panel Dataset。
- 训练共享 LSTM、Embedding、分组 Head、Residual Head 和多任务输出。
- 执行 Walk-forward、Rank IC、Top-K 扣费收益、最大回撤和分层稳定性评估。
- 达标后导出模型参数及元数据，发布到云端 MongoDB 或模型目录。
- 云端交易时段只加载生效制品，禁止自动训练和参数更新。

训练与生产必须使用同一套特征编码规则。股票和行业采用固定哈希桶索引，索引 0 保留给未知值，避免云端依赖动态词表文件；哈希桶数量和算法写入模型元数据，变更时强制升级模型版本。

## 4. 本次模型实现

### 4.1 输入特征

每个时间步共 16 个字段：

- 11 个相对量价/技术指标。
- 股票 Embedding 索引。
- 行业 Embedding 索引。
- 分组 Head 索引。
- 市场标识。
- 成交额流动性。

股票、行业和分组索引不直接进入 LSTM。LSTM 只接收 13 个连续特征，最后时间步的离散索引用于查找可训练向量。

### 4.2 真正的股票和行业 Embedding

- 股票哈希桶默认 8192，Embedding 维度默认 16。
- 行业哈希桶默认 512，Embedding 维度默认 8。
- 未知股票或行业固定映射到索引 0。
- Embedding 参数与 LSTM 主干共同训练并保存在同一模型制品中。

这里的 Embedding 是可训练参数矩阵，不再使用单一哈希浮点数模拟身份特征。

### 4.3 分组 Head

默认 8 个行业/风格分组。每组拥有独立的三维输出校正参数，叠加到共享 Head 的结果。分组数量固定写入元数据；行业缺失时进入默认组 0。

### 4.4 个股 Residual Head

每个股票哈希桶维护轻量三维残差参数，只校正共享输出，不复制 LSTM。默认启用，但残差幅度受配置系数约束。后续应根据样本外增益生成准入掩码，只允许稳定股票使用个股残差；当前版本先提供统一结构和未知股票降级路径。

### 4.5 多任务输出

模型一次输出三个值：

1. `predictedReturn`：缩放后的下一交易日收益率，使用 `tanh` 限幅。
2. `directionProbability`：下一交易日上涨概率，范围 0 到 1。
3. `downsideRisk`：下一交易日下行幅度风险，范围 0 到 1。

训练标签分别为下一日收益率、涨跌方向和负收益幅度。当前组合损失使用收益率 Huber Loss、方向 Binary Cross Entropy 和下行风险 Huber Loss，并通过配置权重控制三个任务的贡献。

## 5. 版本与兼容

本次模型升级为 `v3-embedding-multitask`，特征版本升级为 `panel-embedding-v3`。旧 `v2-panel-return` 制品不能被新代码加载，避免将单输出参数误用于三任务模型。元数据至少校验：

- `modelVersion`
- `featureVersion`
- `labelVersion`
- `sequenceLength`
- `inputSize`
- `outputSize`
- 股票/行业哈希桶数量和 Embedding 维度
- 分组 Head 数量
- Residual Head 开关
- 收益率缩放值

## 6. 运行限制与后续验证

本次只完成结构实现，不声明模型有效性。上线前仍必须完成：

- 多时间窗口 Walk-forward 评估。
- 与无 Embedding、无分组、无 Residual 的消融对比。
- Rank IC、ICIR、Top-K 扣费收益、最大回撤和换手率。
- 行业、市值、市场阶段分层稳定性。
- 云端 2C4G 峰值内存、冷启动和批量推理时延压测。
- 专用验证码模型或人工兜底完成后，重新执行 50 张以上独立样本验收，自动提交准确率必须不低于 85%。
- 模型发布失败、元数据不兼容和本地节点离线时的回退演练。

## 7. 三端目录落地状态

项目代码目录收敛为：

```text
frontend/    React + Vite
backend/     Java 在线业务和推理
python/      Python 3.14 离线训练和 ONNX 制品
docs/        平级系统文档
```

`python/` 默认通过 `training` Profile 按需运行，不随 2C4G 在线服务启动。情感模型默认使用 FP32 ONNX；只有 FP32 实测资源不达标时才评估 INT8，并重新验证强负面召回、候选排序和风控结论。
