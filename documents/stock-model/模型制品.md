# 模型制品

## 制品分类

系统采用两类模型制品管理方式：

| 模型 | 存储方式 | 原因 |
|---|---|---|
| Embedding | `model-artifacts/embedding/<version>` | 固定预训练模型，随代码版本只读发布 |
| Sentiment | `model-artifacts/sentiment/<version>` | 固定财经情感模型，随代码版本只读发布 |
| LSTM | MongoDB GridFS 与激活记录 | 由系统持续训练，需要候选、激活、回滚和审计语义 |

## 固定制品目录

```text
model-artifacts/
├── embedding/
│   └── bge-base-zh-v1.5/
└── sentiment/
    └── finbert-tone-chinese-e91b1a3a/
```

固定制品使用 Git LFS 管理大文件。应用通过配置中的相对路径解析模型版本，Docker Compose 将整个目录只读挂载到 `/app/model-artifacts`。

## 加载方式

`LocalModelArtifactService` 负责解析固定制品目录和版本；Embedding 由 DJL 加载并提供向量能力，Sentiment 由情感制品和推理服务加载。`stock-starter` 在应用启动阶段执行必要的制品预热和状态检查。

加载过程需要区分：

- 路径不存在。
- 版本目录不完整。
- 文件格式不受支持。
- DJL Engine 或本地运行库不可用。
- 模型已加载但推理失败。

## 不可变原则

- 运行时不得下载后覆盖仓库中的固定制品。
- 容器内以只读方式挂载固定模型。
- 升级模型时创建新版本目录，不原地修改旧版本。
- 模型文件、配置、Tokenizer 和校验信息视为一个完整版本。
- 文档不得以“目录存在”推断模型已经成功加载或完成推理。

## LSTM 版本语义

LSTM 不迁移为单纯文件目录，因为其生命周期包含训练运行、模型元数据、二进制参数、激活指针、上一版本和回滚记录。模型制品服务负责将这些信息作为一个整体读取和切换。

## 部署边界

固定制品不打入可执行 JAR，避免扩大 JAR 和镜像层。部署环境必须提供与配置一致的制品目录；缺少 Embedding 时影响 RAG/Memory，缺少 Sentiment 时影响情感推理，但都不应绕过 Java 风控或伪装为可用。
