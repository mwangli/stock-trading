# 模型训练、推理与模型管理架构评估

## 1. 文档信息

| 项目 | 内容 |
|---|---|
| 评估日期 | 2026-10-10 |
| 适用项目 | `stock-trading4` |
| 当前架构 | Java 17 + DJL API + PyTorch Engine |
| 评估范围 | LSTM 训练与推理、模型版本、参数、训练触发、激活、回滚和前端运维入口 |
| 结论状态 | 当前有效设计，覆盖此前 Python/ONNX 迁移方案 |

## 2. 最终架构结论

系统统一采用 Java 模型链路，不维护 Python 工程、ONNX 转换、ONNX Runtime 或独立模型服务。

```text
React 前端
  -> Java Spring Boot
       -> 数据采集与权威特征
       -> DJL Trainer + PyTorch Engine 离线训练
       -> StockLSTMModel 参数加载与在线推理
       -> 策略、风控、幂等和券商交易
       -> MongoDB 模型版本、激活指针和审计数据
```

主要边界：

- LSTM 训练和推理使用相同 Java 模型结构、特征实现和 PyTorch Engine。
- 小型 LSTM 参数、训练配置、输入契约、指标、状态和 SHA-256 保存到 MongoDB。
- 情感 Transformer 权重保存在版本化本地目录，MongoDB 只保存元数据和状态。
- 模型不得直接调用券商，也不得绕过策略、风控、幂等和交易执行。
- 线上节点可以开启训练能力，但训练必须在交易时段之外运行，并通过统一门禁控制。

## 3. 当前实现基线

### 3.1 已具备能力

- `LstmTrainerService` 已支持共享 LSTM 训练、Early Stopping、多任务 Loss 和最佳参数保存。
- `lstm_models` 保存不可变模型版本、训练配置、输入契约、指标、摘要和参数。
- `model_activations` 保存当前版本、上一版本和激活时间。
- 推理加载前校验参数 SHA-256 和模型元数据兼容性。
- `OfflineLstmTrainingJob` 已接入 `JobConfig + JobSchedulerService` 统一调度。
- `LSTM_TRAINING_ENABLED` 已作为节点级训练总开关，默认关闭。

### 3.2 当前缺口

- 没有模型版本列表、版本详情、当前激活版本和上一版本的管理 API。
- 没有独立训练运行记录，无法稳定展示排队、运行、成功、失败、耗时和错误原因。
- 训练成功后当前实现会直接更新激活指针，候选训练与生产发布尚未分离。
- 没有受控激活和回滚 API，也没有操作审计记录。
- 训练参数主要来自 `application.yml` 和环境变量，缺少可审计的单次训练参数快照入口。
- 前端没有模型运维页面，`JobAdmin` 也未形成可用的任务管理入口。

## 4. 是否增加模型管理页面

### 4.1 结论

**需要增加，但应定位为“小型模型运维页面”，不建设通用模型平台或训练管理大屏。**

该页面用于补齐当前已经存在但不可操作、不可审计的模型版本能力：

1. 明确当前生产版本和上一可回滚版本。
2. 查看训练参数、数据范围、指标、摘要和兼容契约。
3. 通过统一门禁提交训练任务，并观察运行状态。
4. 将候选版本的激活与训练成功分离。
5. 在生产版本异常时执行可审计的原子回滚。

### 4.2 不建设的能力

- 通用超参数搜索平台。
- 任意编辑模型结构、特征维度、标签版本或 Engine 版本。
- 浏览器内上传、下载或直接修改模型二进制参数。
- 交易时段即时训练。
- 训练成功后无评估自动覆盖当前生产版本。
- 多级模型审批流、复杂灰度平台和通用实验追踪系统。

## 5. 页面功能范围

建议页面名称为“模型运维”，分为四个页签。

### 5.1 运行概览

- 当前激活模型名称、版本、激活时间和运行状态。
- 上一可回滚版本。
- 最近一次训练状态、耗时、样本数和失败原因。
- 当前节点训练总开关、交易时段门禁和资源门禁状态。
- 参数摘要、元数据兼容性和最近一次加载结果。

### 5.2 版本管理

- 分页查询不可变模型版本。
- 查看训练配置、输入契约、指标、Engine/DJL 版本、参数大小和 SHA-256。
- 标识 `ACTIVE`、`CANDIDATE`、`READY`、`REJECTED`、`ARCHIVED` 状态。
- 对兼容且门禁通过的候选版本执行激活。
- 将激活指针原子回滚到上一版本。

版本文档禁止编辑和覆盖。激活、回滚只修改独立指针和审计记录。

### 5.3 训练任务

- 提交异步训练任务，不在 HTTP 请求线程内直接训练。
- 展示排队、运行、成功、失败、取消和门禁拒绝状态。
- 记录触发人、触发来源、参数快照、开始/结束时间、日志摘要和候选版本 ID。
- 同一模型只允许一个训练任务运行。
- 训练失败或被拒绝时不影响当前激活版本。

### 5.4 训练参数

| 参数类型 | 页面策略 |
|---|---|
| 低风险运行参数 | 允许在受控范围内覆盖，如 `epochs`、`batchSize`、`learningRate`、训练天数 |
| 结构和契约参数 | 只读展示，如 `sequenceLength`、`inputSize`、Embedding 桶数、Head 数、特征版本和标签版本 |

结构和契约参数继续由代码和配置文件管理。修改这类参数必须经过代码审查、版本升级和重新训练，不能通过页面即时修改。

## 6. 线上训练门禁

`LSTM_TRAINING_ENABLED=true` 只表示节点具备训练资格，不代表任何请求都能开始训练。训练入口必须同时满足以下条件：

1. **节点门禁**：当前节点显式开启训练能力。
2. **时间门禁**：不在 A 股交易时段、开盘前候选生成窗口或真实交易任务关键窗口内。
3. **并发门禁**：同一模型没有运行中的训练任务，使用数据库锁或唯一运行记录防止多实例并发。
4. **数据门禁**：交易日历、行情数据、股票池、特征版本和样本量满足要求。
5. **资源门禁**：CPU、可用内存、磁盘和 MongoDB 状态达到最低阈值。
6. **参数门禁**：只接受白名单参数，并限制最小值、最大值和组合关系。
7. **交易门禁**：训练期间不得修改订单、持仓、风控和券商数据。
8. **激活门禁**：训练成功仅生成 `CANDIDATE`，必须经过指标、兼容性和人工确认后才能激活。
9. **回滚门禁**：激活前确认上一版本完整可用，激活失败时保持原指针不变。
10. **审计门禁**：训练、拒绝、激活和回滚都必须记录操作人、原因、参数和结果。

初期建议只允许单节点训练，不支持多个线上实例竞争执行训练任务。

## 7. 后端改造建议

### 7.1 数据模型

新增训练运行记录，例如 `model_training_runs`：

```text
id
modelName
status
triggerSource
triggeredBy
requestedConfigJson
effectiveConfigJson
gateResultJson
startedAt
finishedAt
candidateModelVersionId
errorMessage
createdAt
```

新增模型操作审计记录，例如 `model_operation_audits`，记录训练触发、激活、回滚和门禁拒绝。

### 7.2 状态约定

```text
CANDIDATE -> READY -> ACTIVE
         \-> REJECTED
ACTIVE -> ARCHIVED
```

- `CANDIDATE`：训练已完成，尚未通过发布门禁。
- `READY`：指标和兼容性检查通过，可等待人工激活。
- `ACTIVE`：当前生产版本。
- `REJECTED`：门禁或人工评审不通过。
- `ARCHIVED`：历史版本，仍保留用于审计和必要回滚。

### 7.3 API 边界

建议提供以下 DTO 化接口，全部使用 `ResponseDTO<T>`：

```text
GET  /api/model-operations/overview
GET  /api/model-versions
GET  /api/model-versions/details/{versionId}
GET  /api/model-training-runs
POST /api/model-training-runs/start
POST /api/model-versions/activate/{versionId}
POST /api/model-versions/rollback/{modelName}
```

训练接口只创建异步任务并返回运行 ID。Controller 不直接调用耗时训练方法。

### 7.4 现有行为调整

当前 `LstmTrainerService` 在模型保存成功后立即更新 `model_activations`。开放前端训练入口之前，必须拆分为：

```text
训练完成
  -> 保存不可变 CANDIDATE 版本
  -> 执行指标与兼容性门禁
  -> 标记 READY 或 REJECTED
  -> 人工确认激活
  -> 原子更新 model_activations
```

这是模型运维页面上线的前置条件。

## 8. 前端设计建议

- 在侧边栏增加“模型运维”，不放入普通“设置”页面。
- 默认首屏展示生产状态和最近任务，危险操作不作为视觉主按钮。
- 训练、激活和回滚均使用二次确认，并展示目标版本、当前版本和影响。
- 参数表单只开放低风险白名单字段，结构参数使用只读描述列表。
- 表格支持状态、时间和模型名称筛选，不建设复杂看板。
- 训练运行详情展示阶段、门禁结果和错误摘要，不直接暴露大段原始日志。
- 接口失败时不得使用 Mock 数据冒充真实模型状态，应明确显示“数据不可用”。

## 9. 分阶段实施

### 阶段 1：只读可观测

- 模型概览、版本列表、版本详情、当前激活指针和训练历史。
- 不开放训练、激活和回滚按钮。

### 阶段 2：受控训练

- 增加训练运行记录、异步执行、互斥锁和门禁检查。
- 页面允许提交白名单训练参数。
- 训练产物只进入 `CANDIDATE`，不自动激活。

### 阶段 3：受控发布

- 增加候选评估结果、人工激活、原子回滚和操作审计。
- 仅允许兼容版本激活，不支持跨结构热切换。

### 阶段 4：自动化评估

- 在积累多个真实训练周期后，再增加自动指标比较和发布建议。
- 是否自动激活继续单独评估，默认不开放。

## 10. 验收边界

- 交易时段训练请求被稳定拒绝。
- 多次点击或多实例请求不会启动并发训练。
- 训练失败不会改变当前激活指针。
- 候选版本不能绕过门禁直接激活。
- 激活和回滚均为原子操作，并有完整审计记录。
- 参数越界、数据不足、资源不足和摘要不匹配均能给出明确原因。
- 真实训练期间在线推理、候选生成和交易任务的资源影响处于可接受范围。

## 11. 最终建议

增加模型运维前端页面是必要的，但实施顺序必须是“先补后端状态机和门禁，再开放操作界面”。

推荐范围为：版本查看、参数快照、训练任务、候选激活和上一版本回滚。不要建设通用模型平台，也不要允许页面修改模型结构或在训练成功后自动替换生产模型。

在允许线上训练的前提下，最重要的控制不是开关本身，而是训练与激活分离、交易窗口隔离、单任务互斥、参数白名单和全链路审计。
