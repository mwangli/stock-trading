# 部署与发布

## 运行拓扑

```text
Browser
  → stock-frontend:80
      → /api/** → stock-backend:8080
      → /ws/**  → stock-backend:8080

stock-backend
  → stock-mysql
  → stock-mongo
```

`stock-application` 是唯一 Backend 进程，装配全部 Maven 子模块。Agent 不拥有独立容器、端口、健康检查或发布生命周期。Frontend Nginx 是外部统一入口，Application 端口只按部署配置向必要网络范围开放。

## 发布制品

| 模块 | 构建结果 | 运行容器 |
|---|---|---|
| 模型基础镜像 | Sentiment 与 Embedding 固定模型文件 | Java 17 JRE 基础层 |
| `stock-application` | `stock-application-*.jar`、项目文档，并继承模型基础镜像 | Java 17 JRE，8080 |
| `stock-frontend` | Vite `dist/` | Nginx，80 |

`stock-server/Dockerfile` 同时定义 `models` 和最终 Backend 两个构建目标。模型变化时才下载 Git LFS 并更新模型基础镜像；普通 Backend 发布只在该基础镜像上追加 JAR 和 `documents`，不会重复下载约 1.2GB 模型。生产服务器只拉取最终 Backend 或 Frontend 镜像，不保存独立模型目录，也不维护单独模型服务。

## 配置与持久化

- `.env` 只保存数据库密码、Provider Key、券商凭据和签名密钥等敏感值。
- 数据库地址、端口、库名、用户名、运行开关和普通参数维护在 Application 配置中。
- MySQL 和 MongoDB 使用持久化目录；Servlet Session 与 Caffeine 缓存只存在于当前 Java 进程。
- `docker-compose.yml` 维护服务关系、端口、卷和环境变量注入，不复制业务配置默认值。
- 模型制品随不可变 Backend 镜像发布，运行节点不得在容器外修改模型内容。

## CI/CD

仓库只保留 `.github/workflows/ci-cd.yml` 一个发布工作流：

| 触发条件 | 执行任务 | 目标服务 |
|---|---|---|
| `backend-vX.Y[.Z]` | Backend 构建、推送和部署 | `stock-backend` |
| `frontend-vX.Y[.Z]` | Frontend 构建、推送和部署 | `stock-frontend` |
| `master` 中 `model-files/**` 变化 | 下载 LFS、更新模型基础镜像、重建并部署 Backend | `stock-backend` |

普通 `backend-vX.Y[.Z]` 发布通过 Git 历史定位该版本对应的最近一次模型变更提交，并复用同标签模型基础镜像。构建、推送或部署失败时工作流直接失败；部署成功后只删除被替换的旧应用镜像，不维护工作流间派发、镜像存在性检查、健康轮询或自动回滚。

## 发布验证边界

不同证据必须分开记录：

1. 源码与配置检查只能证明文件关系和声明一致。
2. 镜像构建成功只证明制品可以生成。
3. 容器健康或 HTTP 可达只证明进程入口可用。
4. 数据库、模型、Provider、Quartz、券商和交易任务需要分别核对运行状态。
5. 生产业务终态需要以目标数据、日志、订单和成交事实验证。

本次文档重构只完成源码与文件层检查，未执行构建、镜像发布、容器启动或生产验证。
