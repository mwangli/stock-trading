# 部署与发布

## 运行拓扑

```text
Browser
  → stock-frontend:80
      → /api/** → stock-backend:8080
      → /ws/**  → stock-backend:8080

stock-backend
  → stock-mysql
  → stock-mongo
```

`stock-application` 是唯一 Backend 进程，装配全部 Maven 子模块。Agent 不拥有独立容器、端口、健康检查或发布生命周期。Frontend Nginx 是外部统一入口，Application 端口只按部署配置向必要网络范围开放。

## 发布制品

| 模块 | 构建结果 | 运行容器 |
|---|---|---|
| `stock-application` | `stock-application-*.jar`、项目文档 | Java 17 JRE，8080 |
| `stock-frontend` | Vite `dist/` | Nginx，80 |

`stock-server/Dockerfile` 只构建 Backend 应用镜像，不复制模型文件。生产服务器在部署目录预置 `model-files/`，`docker-compose.yml` 默认把 `./model-files` 只读挂载到容器 `/app/model-files`；模型目录位于其他位置时，通过 `.env` 的 `MODEL_FILES_DIR` 指定绝对路径。应用发布只更新 Backend 或 Frontend 镜像，不下载、复制、打包或移动模型文件。

## 配置与持久化

- `.env` 只保存数据库密码、Provider Key、券商凭据和签名密钥等敏感值。
- 数据库地址、端口、库名、用户名、运行开关和普通参数维护在 Application 配置中。
- MySQL 和 MongoDB 使用持久化目录；Servlet Session 与 Caffeine 缓存只存在于当前 Java 进程。
- `docker-compose.yml` 维护服务关系、端口、卷和环境变量注入，不复制业务配置默认值。
- 固定模型由宿主机目录提供，并以只读方式挂载；更新模型时先完整替换宿主机对应版本目录，再重启 Backend，不在容器内写入或修复模型文件。

## CI/CD

仓库只保留 `.github/workflows/ci-cd.yml` 一个发布工作流：

生产发布只接受三段语义化统一标签 `vX.Y.Z`。每次推送统一版本标签都执行全量发布，不再比较历史标签或检测文件变更范围：

1. `prepare` 任务上传一次 `docker-compose.yml`。
2. Backend 执行 Maven 打包，构建只包含 JAR 与项目文档的应用镜像，并部署 `stock-backend`；服务器上既有模型目录通过 Compose 自动挂载。
3. Frontend 构建应用镜像并部署 `stock-frontend`。
4. Backend 与 Frontend 在 `prepare` 完成后并行执行，不相互等待；两个部署任务都使用 `--no-deps`，只更新自己的应用服务。

手工触发仅用于当前提交的全量补发或故障恢复，不提供 Backend、Frontend 单独发布范围。构建、推送或部署失败时工作流直接失败；部署成功后只删除被替换的旧应用镜像，不自动回滚。

发布示例：

```bash
git tag v5.6.7
git push origin v5.6.7
```

## 发布验证边界

不同证据必须分开记录：

1. 源码与配置检查只能证明文件关系和声明一致。
2. 镜像构建成功只证明制品可以生成。
3. 容器健康或 HTTP 可达只证明进程入口可用。
4. 数据库、模型、Provider、Quartz、券商和交易任务需要分别核对运行状态。
5. 生产业务终态需要以目标数据、日志、订单和成交事实验证。

本次发布流程调整只完成源码、YAML 解析和文件层检查，未执行应用编译、镜像发布、容器启动或生产验证。
