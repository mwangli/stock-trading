# 三类模型持久化与初始化设计

## 1. 结论

本项目采用混合持久化，不再追求三类模型正文必须使用同一种存储：

| 模型 | 正式制品 | 运行加载 | 版本控制 |
|---|---|---|---|
| LSTM | MongoDB GridFS 参数文件 | 从 MongoDB 读取参数到 JVM/DJL 内存 | MongoDB 元数据和激活关系 |
| Embedding | 固定本地目录 | 从固定目录加载到 JVM/DJL 内存 | `application.yml` 版本 + `manifest.json` |
| Sentiment | 固定本地目录 | 从固定目录加载到 JVM/DJL 内存 | `application.yml` 版本 + `manifest.json` |

Embedding 和 Sentiment 都是多文件 Transformer 模型，加载器需要目录结构；它们加载后长期驻留，且版本通常不随每次训练改变。因此，使用 Docker named volume 持久化固定目录，比每次启动从 GridFS 还原临时目录更简单、更省启动 I/O。

## 2. 固定目录契约

```text
/data/models/
├── embedding/
│   └── bge-base-zh-v1.5/
│       ├── config.json
│       ├── tokenizer.json
│       ├── bge-base-zh-v1.5.pt
│       └── manifest.json
└── sentiment/
    └── finbert-tone-chinese-e91b1a3a/
        ├── config.json
        ├── tokenizer.json
        ├── serving.properties
        ├── model.pt
        └── manifest.json
```

正式版本目录由初始化流程维护，禁止人工复制、移动或覆盖。初始化先写入 `<version>.initializing-<uuid>`，完成下载、转换、清单生成、摘要检查和真实加载后，才通过同一文件系统内的原子移动生成正式版本目录。

## 3. 初始化流程

### 3.1 Embedding

1. 检查 `model-path/<model-version>/manifest.json`。
2. 校验模型名称、版本、必需文件、文件大小和逐文件 SHA-256。
3. 校验失败时删除当前损坏版本目录；未开启自动初始化时保持 `NOT_READY`。
4. 从固定 `pretrained-revision` 获取 Hugging Face 原始权重到转换暂存目录。
5. 使用官方 `djl_converter` 输出与模型名一致的 TorchScript 文件 `bge-base-zh-v1.5.pt`。
6. 生成 `embedding-artifact-v1` manifest，并记录原始权重和 TorchScript 权重的大小、SHA-256。
7. `DjlEmbeddingModel` 使用与线上一致的 Tokenizer、Translator 和 `Criteria.loadModel()` 执行真实加载校验。
8. 实际加载成功后原子移动到正式版本目录，并保持模型对象常驻内存。

### 3.2 Sentiment

1. 执行与 Embedding 相同的固定目录检查流程；默认从 `model-artifacts` 读取，不启用远程下载。
2. Java 从固定 `model-artifacts` 制品目录复制已经转换完成的 `.pt` 文件，不再在启动时调用 `djl-convert`；复制前后均通过 manifest、文件大小和 SHA-256 校验确认制品完整。
3. 固定目录必须包含与模型名匹配且可读的 `.pt` 权重；缺失、摘要不匹配或不可加载时初始化失败。
4. 生成 `sentiment-artifact-v1` manifest，记录来源仓库、revision、引擎、标签顺序、序列长度、文件大小和 SHA-256。
5. `SentimentArtifactService.inspectForLoad()` 完成清单检查，`SentimentTrainerService` 再用 DJL `Criteria.loadModel()` 实际加载。
6. 只有固定制品完整性检查和实际加载全部成功，才原子移动到正式版本目录。

Java 可以负责固定制品的生命周期、日志、摘要校验和 DJL 加载校验，但不在在线运行时执行 Hugging Face Transformer 到 TorchScript 的转换。转换只在制品构建环境完成；生产运行时只接收已经验证的 `<model-name>.pt`。缺少匹配 `.pt`、摘要不一致或加载失败时，系统保持未就绪，不得把原始 `safetensors`、`pytorch_model.bin` 或普通权重误标记为可加载模型。

### 3.3 如何确认预转换制品可信

仅凭文件名 `model.pt` 不能确认制品可信。初始化必须同时满足：

1. `pretrainedRevision` 使用不可变提交，不使用 `main` 或其他浮动分支。
2. 固定制品目录中的文件摘要必须与 manifest 一致，manifest 本身不参与文件清单摘要。
3. 生成的 manifest 再记录实际文件大小和 SHA-256，后续启动重复校验。
4. 使用与线上相同的 DJL `Criteria`、PyTorch Engine、Tokenizer 和 Translator 实际加载。
5. 加载成功后才原子移动到 `/data/models/sentiment/<version>`。

## 4. 三种持久化方案比较

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 当前混合方案 | LSTM 适合训练版本和回滚；Embedding/Sentiment 重启后直接读本地目录；启动 I/O 最少 | 有两套制品治理流程；模型本地卷需要备份和容量监控 | 当前项目最合适 |
| 三类都保存文件 | 加载路径直接、实现简单；可统一通过卷恢复 | LSTM 训练节点与线上节点需要共享/迁移文件；版本激活关系需要额外文件或数据库；容易产生人工迁移 | 不适合 LSTM 的候选、激活和回滚场景 |
| 三类都保存 GridFS | 制品集中、跨容器一致、版本回滚统一 | Embedding/Sentiment 每次重建或重启都要下载/还原数百 MB；多文件目录加载复杂；Mongo 磁盘和网络压力更高 | 只有多节点统一制品平台时才值得采用 |

## 5. MongoDB 元数据和激活关系是否必要

### LSTM：必要

LSTM 是训练产物，版本会持续变化，并且需要候选、已激活、回滚、训练快照、参数摘要和兼容性校验。没有 `model_metadata` 和 `model_activations`，系统无法可靠判断当前线上应加载哪一个 GridFS 参数文件，也无法在训练成功后保持“候选不自动上线”的边界。

### Embedding/Sentiment：当前方案不是必需

这两个模型的正式版本由 `application.yml` 固定，目录由 `manifest.json` 自描述。没有 MongoDB 元数据时，系统仍可通过以下信息工作：

- 配置中的 `modelPath` 和 `modelVersion`；
- manifest 中的模型名称、版本、来源、文件清单和摘要；
- DJL 实际加载结果和运行时健康状态。

缺少元数据的代价是无法在 MongoDB 中统一查询“当前节点加载了哪个版本”、无法记录跨节点激活历史，也不能通过数据库指针远程切换版本。由于这两个模型当前不允许人为迁移文件，且版本切换通过配置变更后重新初始化完成，因此本期不为它们增加激活关系，避免重复保存固定信息。

如果未来需要多节点灰度、远程回滚、审批发布或按租户切换版本，再为 Embedding/Sentiment 增加独立的 MongoDB `model_activation` 关系；届时仍不建议把大文件正文迁入 GridFS，元数据和正文可以分开。

## 6. 容器和磁盘策略

- Compose 使用 `model-runtime:/data/models` named volume，不使用宿主机项目目录 bind mount。
- 容器重建不会重复下载已完成且摘要有效的版本目录。
- 版本目录按版本保留；切换版本会增加一份模型占用，删除旧版本前必须确认没有运行中的加载任务。
- 初始化暂存目录失败后必须清理；异常残留的 `.initializing-*` 目录可在下次初始化前清理。
- 磁盘容量至少按 Embedding、Sentiment 当前版本各一份，再加一个转换暂存副本和安全余量估算；没有预转换文件时，转换过程中可能短暂出现“原始权重 + 转换输出”双份占用。
- LSTM 参数仍保存在 MongoDB GridFS，训练快照和版本记录不写入本地模型卷。

## 7. 异步可用性和失败语义

应用先启动 HTTP 服务，`ApplicationReadyEvent` 后异步初始化和预热模型。模型未完成转换、完整性校验或 DJL 加载时，服务可以存活，但依赖模型的接口必须返回明确的未就绪状态，不能返回规则结果或随机向量伪装成真实模型结果。

本设计不保留 LSTM 训练断点恢复制品。训练中断后从头开始；数据快照和已完成模型版本仍可复用，但不表示恢复优化器状态或中间 Epoch。

## 8. 验证边界

源码和配置检查可以确认调用链、目录契约、容器卷和失败分支；不能替代以下运行证据：

- 发布制品已在构建阶段完成格式转换并包含匹配的 `.pt` 文件；
- DJL `Criteria.loadModel()` 实际加载成功；
- named volume 重启后目录仍存在；
- 大模型下载、转换和加载的真实耗时及磁盘峰值。
