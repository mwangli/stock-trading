# 四模块总体架构设计

## 逻辑结构

```text
React 前端
    -> 数据采集 API
    -> 模型服务 API
    -> 智能决策 API
    -> 交易执行 API

Java Spring Boot 单体
    dataCollector -> modelService -> strategyAgent -> tradingExecutor -> 券商
                                                        tradingExecutor（认证、运行配置、调度）

MySQL：用户、运行配置、任务、策略和交易事实
MongoDB：行情、新闻、训练快照、模型元数据、GridFS 模型制品和预测结果
```

## 目标包结构

后端只保留四个顶层业务包：`dataCollector`、`modelService`、`strategyAgent`、`tradingExecutor`。`strategyAgent` 合并原策略分析能力和 Agent 研究、诊断、对话及交易决策能力。现有 `systemConfig`、`user` 和调度能力统一归入 `tradingExecutor`，按 `api`、`config`、`domain`、`persistence`、`service`、`web` 等职责目录组织，调度类直接位于 `tradingExecutor` 根包。

## 依赖方向

允许数据采集被模型和智能决策读取，允许模型结果被智能决策读取，允许智能决策结果被交易执行读取。禁止反向调用和环状依赖；交易执行需要市场事实时通过数据采集查询接口读取，不直接修改其持久化对象。依赖方向固定为 `dataCollector -> modelService -> strategyAgent -> tradingExecutor`，这里的箭头表示后一个模块依赖前一个模块，后置层可以读取前置层的公开 DTO、查询服务或端口，前置层不得反向依赖后置业务实现。运行开关、统一调度等横向支撑能力通过端口和适配器接入，不改变四个业务模块的递进关系。

`TradePlanExecutionService` 和 `TradeExecutor` 都属于 `tradingExecutor`。前者负责交易计划的二次取数、执行门禁和状态转换，后者负责风险检查和券商执行；它们之间是同一模块内的职责协作，不是跨模块依赖，因此不应为了形式上的解耦移除 `TradeExecutor` 依赖。跨模块边界只约束 `strategyAgent` 不直接注入或调用 `TradeExecutor`。

## 统一约束

- 所有后台任务由 `tradingExecutor` 根包中的固定 Quartz Job 管理。
- 所有接口使用 DTO 和 `ResponseDTO<T>`。
- 认证只解决访问身份，运行配置只解决节点开关，风控和真实写入门禁仍由交易执行独立判断。
- 失败按模块关闭：数据失败停止计算，模型失败停止候选，智能决策失败停止交易计划，风控或券商失败禁止委托。
- 模型正文统一由 MongoDB GridFS 持久化，普通集合保存模型元数据、文件清单、摘要和激活指针。LSTM 参数可直接从 GridFS 读入内存，Embedding/Sentiment 多文件模型仅在 DJL 加载期间使用系统临时目录。
- 应用启动不等待大模型下载和加载；`ApplicationReadyEvent` 之后异步预热，模型未就绪时返回明确状态，不使用伪造结果。Docker 不挂载本地模型目录。
