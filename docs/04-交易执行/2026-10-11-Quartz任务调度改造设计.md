# Quartz 任务调度改造设计

## 1. 改造目标

将现有 `JobConfig + JobSchedulerService + ThreadPoolTaskScheduler` 改造为 Quartz 调度实现，同时保留项目的固定任务和业务门禁边界，新增：

1. 任务运行状态查询；
2. 固定任务白名单下的受控手动触发；
3. 独立执行记录和历史分页查询；
4. Quartz 调度状态与业务执行状态分离；
5. 为未来多实例部署保留持久化调度和互斥扩展能力。

本次不建设通用任务编排平台，不允许页面任意编辑 Cron、Bean 名称、方法名或任务参数。

## 2. 当前实现问题

当前调度器只在启动时加载 `job_config`，使用本地 `ScheduledFuture` 保存调度句柄，并将执行结果覆盖写回任务配置。它没有独立运行记录，也没有统一的任务管理 Controller；应用重启或多实例部署时，运行态和执行历史无法完整恢复。

模型训练已有独立运行记录和门禁链路，普通任务应采用相同的“定义、运行、审计”分离方式。

## 3. 总体架构

```text
固定任务定义 JobConfig
    |
JobSchedulerService
    |
Quartz Scheduler
    |-- JobDetail: stable jobName
    |-- CronTrigger: cronExpression + misfire policy
    v
QuartzJobAdapter
    v
JobExecutionService
    |-- triggerSource / operator / runId
    |-- concurrency gate
    |-- business gate
    |-- JobExecutionRecord
    v
现有 DataSyncScheduler / StrategyScheduler / RealTradingJob / OfflineLstmTrainingJob
```

Quartz 只负责调度生命周期；`JobExecutionService` 负责业务执行状态、并发控制、异常归一化和审计。

## 4. 任务定义与注册

- `JobConfig` 继续保存 `jobName`、Cron、启用状态、Bean 名称和方法名称。
- `JobBootstrap` 继续负责固定任务的幂等初始化。
- 每个固定 `jobName` 必须建立独立的 Quartz Job 类，并显式加入 `JobSchedulerService.JOB_CLASSES`，禁止回退到 Bean 和方法反射调用。
- 任一 Bootstrap 保存或更新 `JobConfig` 后必须立即调用统一注册方法，幂等创建或更新对应的 `JobDetail` 和 `CronTrigger`。
- 主 `JobBootstrap` 在全部默认配置初始化后再次执行全量注册，作为启动顺序和局部注册失败的兜底重试。
- 注册失败必须按任务记录明确错误，不能因为单个任务失败而跳过其他固定任务。
- 禁用任务从 Quartz 中暂停，不删除 `JobConfig` 和历史记录。
- 任务标识使用 Quartz group + `jobName`，不得使用随机 UUID，保证重启后可更新同一任务。
- `beanName` 和 `methodName` 只来自代码维护的任务白名单，不接受 HTTP 动态传入。

## 5. 运行记录模型

新增 MySQL 表 `job_execution_record`，每次触发生成一条记录：

| 字段 | 说明 |
|---|---|
| `run_id` | 公开查询用的唯一运行标识 |
| `job_name` | 固定任务名称 |
| `trigger_source` | `SCHEDULED`、`MANUAL` 或 `RECOVERY` |
| `triggered_by` | 操作人或系统标识 |
| `scheduled_time` | 计划触发时间 |
| `queued_time` | 创建排队记录时间 |
| `started_time` | 实际开始时间 |
| `finished_time` | 实际结束时间 |
| `duration_ms` | 执行耗时 |
| `status` | 运行状态 |
| `error_type` | 脱敏后的异常类型 |
| `error_message` | 脱敏后的错误摘要 |
| `result_summary` | 结果摘要，不保存敏感参数 |
| `host_name` | 执行节点标识 |
| `created_at` | 记录创建时间 |

运行状态定义：

```text
QUEUED -> RUNNING -> SUCCESS
                  -> FAILED
                  -> CANCELLED
                  -> SKIPPED
                  -> REJECTED
```

## 6. 任务状态查询

任务列表需要同时展示两类状态。

### 调度状态

```text
ENABLED / DISABLED / PAUSED / ERROR
```

来源是 `JobConfig` 与 Quartz Trigger 状态。

### 执行状态

```text
IDLE / QUEUED / RUNNING / SUCCESS / FAILED / REJECTED / CANCELLED
```

来源是最近一条 `JobExecutionRecord` 以及当前未结束记录。

不能仅使用 Quartz 的 Trigger 状态代表业务运行状态，也不能仅使用 `job_config.last_status` 代表历史状态。

## 7. 手动触发与停止执行

手动触发接口只接受路径中的固定 `jobName`，服务端执行以下校验：

1. 任务存在且已注册为固定 Quartz Job。
2. 任务未被禁用或暂停。
3. 同一任务没有排队或运行中的记录。
4. 创建 `MANUAL` 类型执行记录。
5. 调用 Quartz `triggerJob`，由 Quartz 线程执行固定任务。

所有已注册固定任务均允许手动触发，但真实交易任务仍不得绕过：

- `TRADING_REAL_WRITE_ENABLED`；
- 券商登录和会话有效性；
- 交易时间；
- 资金、持仓、可成交性和重复委托风控；
- 订单与成交幂等逻辑。

停止执行按 `runId` 操作：

- `QUEUED` 记录直接更新为 `CANCELLED`，Quartz 后续取出任务时必须跳过业务执行；
- `RUNNING` 记录先更新为 `CANCELLED`，再通过 Quartz 中断当前 Job 执行线程；
- Java 线程中断属于协作式中断，业务循环、等待和批处理必须检查中断标记或正确传播 `InterruptedException`；
- 已结束任务不能重复停止，停止操作必须记录操作人、完成时间和结果摘要。

`QUEUED` 状态继续保留。触发接口和 Quartz 工作线程是异步关系，排队状态用于表达“已受理但尚未开始”、阻止同任务重复提交，并允许取消尚未获得工作线程的任务。

## 8. 查询接口

```text
GET  /api/jobs
GET  /api/jobs/details/{jobName}
GET  /api/jobRuns
GET  /api/jobRuns/details/{runId}
POST /api/jobs/trigger/{jobName}
POST /api/jobs/pause/{jobName}
POST /api/jobs/resume/{jobName}
POST /api/jobRuns/stop/{runId}
```

响应统一使用 `ResponseDTO<T>`。分页查询支持任务名称、状态、触发来源、开始和结束时间、`current`、`pageSize`。

所有写操作必须记录 Controller 入口日志、操作人和执行结果。

## 9. 并发与恢复策略

- 默认同一 `jobName` 禁止并发执行；需要允许并发的任务必须显式登记。
- Quartz 层使用禁止并发执行配置，应用层再使用数据库运行记录校验，形成双重保护。
- 任务执行异常必须解包 `InvocationTargetException`，保存根异常类型和消息摘要。
- 应用启动时扫描长时间停留在 `RUNNING` 的记录，按恢复策略标记为 `FAILED` 或 `CANCELLED`。
- 数据同步类任务可以配置有限 misfire 补偿。
- 真实买入、真实退出和模型激活任务禁止错过后自动补执行。

## 10. 替代框架评估

| 方案 | 优点 | 缺点 | 本项目建议 |
|---|---|---|---|
| Spring `ThreadPoolTaskScheduler` | 无新增中心组件，改造简单 | 无持久化 Trigger，集群防重和 misfire 需自建 | 单实例轻量方案 |
| Quartz | JDBC 持久化、暂停恢复、misfire、多实例扩展成熟 | 配置和表结构较复杂，业务记录仍需自建 | 当前采用 |
| ShedLock + Spring Scheduler | 保留现有 Spring 代码，只补分布式锁 | 不提供完整任务中心和执行历史 | 若只需要防重复可选 |
| XXL-JOB | 自带调度中心、Web 管理、执行器和日志 | 引入独立中心组件，部署和运维成本增加 | 多服务、多团队场景再考虑 |
| PowerJob | 支持分布式任务、工作流和大规模调度 | 能力和组件规模明显超出当前项目 | 当前不建议 |
| Temporal | 工作流、长任务、重试和状态持久化能力强 | 引入服务端、Worker 和新的编程模型 | 不适合当前简单 Cron 任务 |

本项目选择 Quartz，是因为目标是增强当前单体内的持久化调度能力，而不是建设独立调度平台。若未来主要需求变成跨多个服务统一运维，应重新评估 XXL-JOB 或 PowerJob。

## 11. 验收标准

- 应用启动后固定任务能够创建或更新 Quartz Job 和 Trigger。
- 禁用任务不会触发，暂停和恢复不会删除历史记录。
- 查询任务时能看到调度状态、最近一次运行状态和下一次触发时间。
- 手动触发只能使用白名单任务，并返回唯一 `runId`。
- 每次定时或手动执行都能生成独立记录。
- 执行成功、失败、门禁拒绝、跳过和取消都有明确状态。
- 分页查询可以按任务、状态、来源和时间范围查询历史。
- 任务异常不会导致 Quartz 调度线程永久失效。
- 真实交易任务手动触发不能绕过交易和风控门禁。
- 编译验证通过，且完成单节点重启、重复触发和异常任务的运行验证。
