# 情感分析数据源补充设计

## 1. 设计目标

在现有 `StockNewsService` 和 `SentimentAggregationService` 之上增加可插拔的数据源适配层。各来源负责请求、解析和标准化，统一事件模型负责去重、保存、时间截断和下游情感分析；来源之间互相隔离，单个来源异常不得覆盖其他来源的成功结果。

## 2. 总体架构

```text
证券平台新闻/公告 ─┐
东方财富公告      ├─> 来源适配器 ─> 标准化事件 ─> 去重与水位 ─> MongoDB
东方财富业绩      │                                      │
东方财富监管/股东 ─┘                                      ├─> 情感推理
                                                         └─> 事件聚合/交易门禁
```

建议新增以下逻辑边界：

- `SentimentSourceAdapter`：描述来源名称、支持的事件类型和分页能力。
- `EastmoneyAnnouncementAdapter`：负责公司公告和公告正文。
- `EastmoneyCompanyEventAdapter`：负责业绩、监管、股东/高管和重大经营事件。
- `SentimentEventNormalizer`：将不同响应结构转换为统一事件。
- `SentimentEventSyncService`：执行增量水位、限流、重试、幂等写入和批次统计。

具体东方财富请求地址和字段映射必须放在适配器配置或版本化解析器中，不应散落在情感聚合代码中。

## 3. 统一事件模型

事件模型至少包含以下业务字段：

| 字段 | 说明 |
| --- | --- |
| `stockCode` | 关联股票代码 |
| `stockName` | 采集时的股票名称快照 |
| `source` | 数据来源，如现有证券平台或东方财富 |
| `sourceVersion` | 来源页面、接口或解析器版本 |
| `sourceEventId` | 来源事件编号；没有时为空 |
| `eventType` | 业绩、监管、股东/高管、经营、资金风险等分类 |
| `title` | 原始标题 |
| `content` | 原始正文或详情摘要 |
| `normalizedText` | 供模型输入的清洗文本 |
| `publishedAt` | 来源发布时间 |
| `collectedAt` | 本地采集时间 |
| `contentHash` | 标题和正文规范化后的内容指纹 |
| `informationPriority` | 信息优先级，P0/P1/P2 或对应数值 |
| `rawPayload` | 必要时保留的原始响应片段，用于字段变更排查 |

现有 `StockNews` 可以继续兼容已有新闻和公告数据；新增字段优先复用 `eventType`、`contentHash` 和 `informationPriority`。若后续需要保存来源版本和原始响应，应通过增量字段扩展，不改变现有唯一键语义。

## 4. 来源适配

### 4.1 公司公告

优先采集公告标题、公告编号、公告日期、公告类型、来源机构和正文。公告正文为空时保留标题并标记 `contentMissing=true`，不得伪造正文。公告详情请求失败只影响该条记录，列表水位按来源结果规则处理。

### 4.2 业绩信息

从公告分类或公司事件模块识别业绩预告、业绩快报、定期报告、净利润变化和营业收入变化。结构化数值应保留为事件属性，文本正文仍作为情感模型输入；数值字段不能直接替代正文情感判断。

### 4.3 监管与诉讼

重点识别监管问询、监管处罚、立案调查、违规处理、诉讼仲裁、退市风险、债务违约和审计意见异常。该类事件设置高优先级，并在聚合阶段保留强负面短路判断。

### 4.4 股东与高管变动

识别股东增持、减持、质押、解禁，以及董事、监事、高管任免和持股变化。事件必须区分“发生日期”和“公告日期”，预测截止时间判断使用对市场可见的公告时间。

### 4.5 重大经营与资金风险

识别重大合同、订单、中标、投资、并购、合作、融资融券、龙虎榜、大宗交易和股权质押。此类事件作为情感和风险辅助信息，不能未经验证直接改变交易执行开关。

## 5. 增量同步与幂等

每个来源、每只股票独立维护同步状态：最近尝试时间、最近成功时间、最大已知发布时间、连续无变化次数、错误码和下次重试时间。同步顺序为：

1. 读取来源水位和信息截止时间。
2. 请求列表或分页数据。
3. 解析并校验股票代码、标题、发布时间和来源事件编号。
4. 请求详情并生成标准化事件。
5. 先按 `stockCode + source + sourceEventId` 去重，再按 `contentHash` 合并跨来源重复事件。
6. 成功写入后才推进该来源水位。
7. 记录新增数、重复数、空正文数、失败数和重试时间。

任务必须使用统一调度中心注册，建议将公告、业绩/监管事件和低频公司画像拆成独立任务，避免一个来源故障阻塞全部情感数据。

## 6. 情感聚合接入

`SentimentAggregationService` 接收经过 `informationCutoffAt` 过滤的标准化事件：

- 先按 `contentHash` 或事件指纹分组。
- 同一事件只选择正文最完整、来源可信度最高的一条作为模型主输入。
- `REGULATORY_OR_LITIGATION`、重大业绩异常和退市/违约类事件使用高权重，并允许触发强负面门禁。
- `SHAREHOLDER_OR_EXECUTIVE`、`MATERIAL_BUSINESS` 和 `CAPITAL_RISK` 使用中高权重。
- 普通新闻和一般公告使用基础权重。
- 事件缺少正文时可以参与规则型风险识别，但不能把空正文送入模型推理。

聚合结果必须保留：事件数量、去重后事件数量、最高优先级事件类型、强负面标题、模型版本和信息截止时间。

## 7. 失败处理与观测

来源响应为空、超时、限流、鉴权失败、字段结构变化、详情缺失和 MongoDB 写入失败必须使用不同错误码。失败来源进入有限重试和退避；达到重试上限后保持缺口，不得把水位推进到失败位置。

至少记录以下指标：

- 每来源请求数、成功数、空响应数、超时数和限流数。
- 每股票新增事件数、重复事件数、正文缺失数和解析失败数。
- 各事件类型占比及最近发布时间。
- 情感推理输入数、跳过数、强负面事件数和模型失败数。

## 8. 版本与验证边界

东方财富接口属于网页后台数据源，接入时必须保存来源版本和样本响应，先完成字段字典、分页一致性、详情关联、发布时间口径和限流行为验证，再启用生产任务。源码设计完成不等于接口可用；必须通过实际接口响应、数据库落库记录和情感聚合结果分别验证。
