# 03-智能决策 Agent 设计

## 总体架构

```text
React / API Client
        |
        v
AGENT Controller -> AgentApplicationService
        |                    |
        |                    +-> Session / Task / Audit Repository (MySQL)
        |
        v
Agent Runtime
  ContextAssembler -> LLM Provider Adapter -> StructuredOutputValidator
        |
        v
Tool Gateway -> Read-only Tool Services
        |          |          |          |          |
 dataCollector modelService strategyAgent tradingExecutor 运行审计
        |
 MySQL / MongoDB 事实数据
```

AGENT 是 `strategyAgent` 模块中的智能决策子域，代码归属于 `com.stock.strategyAgent` 下的 Agent 相关子包。它只能通过各模块公开的查询服务或 DTO 读取数据，不引用 `tradingExecutor` 的执行服务、券商适配器或可写交易 Entity。

推荐子包：

```text
com.stock.strategyAgent
├── strategy            # 确定性策略分析、候选、信号和回测
├── agent               # Agent 应用编排、对话和交易计划决策
├── api                 # Controller、Request、Response DTO
├── application         # 会话、任务、报告和诊断编排
├── runtime             # Agent Loop、上下文、模型 Provider、超时策略
├── tool                # ToolDefinition、ToolGateway、只读工具实现
├── domain              # 会话、任务、计划、状态和审计模型
├── persistence         # MySQL Repository 和 Mongo 只读查询适配
└── config              # Agent 开关、模型、配额和脱敏配置
```

## 运行模式

### Research 模式

Research 模式处理单次问题或固定报告任务。执行循环限定为：

```text
创建任务
  -> 组装系统约束和用户问题
  -> 模型选择只读工具
  -> 校验工具参数
  -> 执行工具
  -> 写入证据摘要
  -> 模型生成结构化答案
  -> 校验引用和敏感字段
  -> COMPLETED / FAILED / NEEDS_REVIEW
```

模型不能自行决定新增工具、修改工具 Schema 或改变最大步数。建议一期默认每次任务最多 6 次工具调用、最多 3 轮模型请求，具体值由配置限制并写入任务快照。

### Diagnostic 模式

Diagnostic 模式使用固定检查器优先于自由推理。检查器按以下顺序返回结构化事实：

```text
TradingCalendarChecker
  -> DataCompletenessChecker
  -> PredictionBatchChecker
  -> StrategyRunChecker
  -> RiskGateChecker
  -> JobExecutionChecker
```

模型只负责把检查结果组织成中文结论、证据列表和下一步建议，不负责重新计算交易日、风控或任务状态。每个检查器必须返回 `PASS`、`WARN`、`BLOCKED` 或 `UNKNOWN` 及原因。

### Report 模式

每日投研报告使用固定 Report Schema 和模板，避免完全由模型自由发挥：

```text
MarketOverview
CandidateSummary
ModelSignals
SentimentSignals
StrategyState
RiskWarnings
DataQuality
JobAnomalies
EvidenceReferences
Uncertainty
```

报告生成任务由 `tradingExecutor` 根包中的统一调度体系触发。AGENT 只提供无参 Job 方法和应用服务，不使用 `@Scheduled`。报告生成失败不会影响数据采集、模型、策略和交易主链路。

### Autonomous Trade 模式

二期增加 `TradePlan`，移除人工审批，执行链路固定为：

```text
Agent -> TradePlanValidator
      -> tradingExecutor 重新读取当前事实
      -> RiskController
      -> TradeExecutor
      -> ZXBrokerAdapter
```

Agent 不得返回券商订单字段，不得返回可直接反序列化为下单请求的对象。`TradePlan` 必须包含 `planId`、候选批次、证据引用、有效期和幂等键。计划落库后由 `TradePlanExecutionJob` 或候选触发任务自动处理，不等待用户确认。

执行状态如下：

```text
PENDING_REVALIDATION -> RISK_REJECTED
                     -> EXECUTING -> EXECUTED
                                  \-> FAILED
PENDING_REVALIDATION -> EXPIRED
```

`TradePlanValidator` 只校验结构、来源、有效期、证据和计划内部一致性；交易可执行性必须由 `tradingExecutor` 重新读取当前行情、交易日历、账户、持仓、券商订单和运行配置后判断。真实交易批次使用数据库唯一幂等键，计划重试不得重复创建券商委托。

## Tool Gateway 设计

### 工具定义

每个工具由不可变 `ToolDefinition` 描述：

```text
name
version
description
inputSchema
outputSchema
requiredPermission
readOnly
maxResultSize
timeoutMs
redactionPolicy
```

`ToolGateway` 负责名称白名单、JSON Schema 参数校验、权限判断、超时、结果大小、敏感字段脱敏、审计和错误归一化。工具实现只能调用领域查询服务，不允许把任意 SQL、Mongo 查询表达式或 URL 交给模型。

### 一期工具边界

- `PredictionTool`：查询已完成预测批次、模型版本、股票预测明细和批次统计。
- `StrategyTool`：查询候选排名、策略配置版本、策略评估和回测摘要。
- `NewsSentimentTool`：查询新闻、公告、情感聚合和信息截止时间。
- `JobDiagnosticTool`：查询固定任务定义、运行记录、状态、错误摘要和触发来源。
- `TradingCalendarTool`：查询交易日、确认状态、休市原因和来源版本。
- `RiskReadTool`：查询已经产生的风控决策、门禁结果和脱敏账户快照。
- `BrokerSnapshotTool`：查询只读账户、持仓和订单事实，不获取登录凭据，不触发券商请求写入。

工具返回统一的 `ToolExecutionResult<T>`：

```text
success
status
source
asOf
data
warnings
errorCode
traceId
```

`data` 必须是明确 DTO，不使用 Controller 层的裸 `Map`。查询无结果和工具失败必须区分，避免模型把“没有记录”理解成“业务正常”。

## Provider 与模型适配

定义 `AgentModelProvider` 接口，至少包含：

```text
complete(AgentPrompt prompt, ModelCallOptions options)
stream(AgentPrompt prompt, ModelCallOptions options)
getProviderMetadata()
```

一期实现两个适配方向：

- `DeepSeekProvider`：通过受控 HTTP 客户端调用兼容 API，支持 Tool Calls、结构化输出、超时和重试上限。
- `OllamaProvider`：作为本地模型可选适配器，不作为一期必需部署组件。

DeepSeek Harness 只作为未来可替换的运行时或插件实现，不直接侵入领域服务。Provider 返回统一的 `ModelCallResult`，记录模型名称、版本、耗时、Token 摘要、停止原因和错误类型；不记录密钥和完整敏感 Prompt。
## RAG 设计

### RAG 数据边界

二期不增加独立向量库，继续使用现有 MongoDB 保存文档、Chunk、Embedding 和检索元数据，并建立 MongoDB 向量检索索引。RAG 数据分为四类：

```text
制度与系统文档 -> 文档知识
新闻、公告、行业材料 -> 市场背景
历史投研报告与诊断报告 -> 经验资料
Agent 记忆 -> 用户偏好、历史事件、交易复盘；Memory 的语义索引也保存在 MongoDB
```

实时价格、账户、持仓、订单、风险门禁、交易日历和任务状态不以向量检索作为事实来源，必须通过结构化 Tool 查询。

### 摄取流水线

```text
原始内容
  -> 来源校验和脱敏
  -> 文档版本与内容哈希
  -> 按标题、段落和语义边界切分 Chunk
  -> Embedding
  -> MongoDB 文档写入和向量索引更新
  -> 记录索引版本和失败状态
```

每个 Chunk 的 payload 至少包含 `sourceType`、`sourceId`、`version`、`publishedAt`、`asOf`、`stockCodes`、`tags`、`visibility`、`contentHash` 和 `embeddingModelVersion`。同一来源的新版本不能覆盖旧版本，必须通过版本和有效状态控制检索。

### 检索流水线

```text
用户问题
  -> 意图识别和权限范围
  -> Query Rewrite
  -> 向量召回
  -> 时间、来源、股票和权限过滤
  -> 可选重排
  -> 去重和上下文压缩
  -> EvidenceReference
  -> LLM
```

RAG 结果必须带来源和时间，回答只能引用本次检索返回的 Chunk。检索结果不足、来源冲突或版本过期时，返回不确定状态；不能用模型常识补全市场事实。Prompt Injection 文字视为不可信资料，不得改变系统指令、工具权限或执行策略。

### RAG 生命周期

- 文档新增、更新、删除和重新 Embedding 都产生审计记录。
- Embedding 模型升级时建立新索引版本，完成抽样检索比对后再切换读取指针。
- 删除或撤回来源时，先将来源标记为不可检索，再异步清理向量。
- MongoDB 中的向量检索不作为交易正确性的唯一依赖；MongoDB 向量检索不可用时，Research 可降级为结构化工具和 MongoDB 文本查询，自动交易计划必须因证据不足而停止生成或拒绝执行。

## Memory 设计

### 记忆分层

```text
会话记忆       Session Memory       当前对话临时上下文
用户偏好       Preference Memory    用户明确确认的分析和交易偏好
语义记忆       Semantic Memory      稳定的系统知识、规则和术语
事件记忆       Episodic Memory      历史任务、诊断和报告事件
交易复盘记忆   Trading Memory       计划、风控、成交和复盘结果
```

会话记忆默认短期保存；用户偏好、事件记忆和交易复盘必须有来源、置信度、创建时间、更新时间、有效期和删除状态。模型自动生成的推断不能直接提升为用户偏好或交易规则。

### 记忆写入规则

记忆写入统一经过 `MemoryService`：

```text
候选记忆
  -> 类型和 Schema 校验
  -> 敏感字段检测与脱敏
  -> 来源和置信度绑定
  -> 去重、冲突检测和 TTL 计算
  -> MySQL 元数据 + MongoDB Chunk/Embedding 文档
  -> 审计记录
```

以下内容禁止写入长期记忆：密码、Token、Cookie、券商会话、私钥、完整账户敏感字段、未经确认的交易指令和无法追溯来源的模型猜测。用户明确表达的偏好可以写入，但必须标记为 `USER_CONFIRMED`；系统推断标记为 `MODEL_INFERRED`，默认不能影响真实交易参数。

### 记忆召回规则

`MemoryRetriever` 根据任务类型选择记忆范围：

- Research：召回相关历史分析、用户关注股票和报告偏好。
- Diagnostic：召回同类任务失败、历史异常和已确认解决方案。
- Report：召回报告模板、用户关注维度和历史对比窗口。
- Autonomous Trade：只允许召回已确认的风险偏好和历史复盘摘要，不能用记忆覆盖实时账户、当前策略配置、风险限额或交易日判断。

每条召回记忆必须带 `memoryId`、类型、来源、有效期、置信度和内容摘要。过期、冲突或低置信记忆不得进入交易计划的硬约束，只能作为背景提示。

### 记忆管理接口

建议提供：

```text
GET    /api/agent/memories
GET    /api/agent/memories/{memoryId}
DELETE /api/agent/memories/{memoryId}
POST   /api/agent/memories/{memoryId}/correct
POST   /api/agent/memories/{memoryId}/forget
```

接口只能操作当前用户有权访问的记忆；删除采用逻辑删除并同步标记向量不可检索。纠错必须保留原记忆版本和修正来源，不能直接覆盖历史审计。

## 上下文和证据设计

`ContextAssembler` 只向模型提供任务需要的最小上下文：系统规则、用户问题、工具 Schema、工具结果摘要、证据引用和输出格式。原始新闻正文、完整账户字段和完整日志默认不直接注入，先由工具截断、脱敏和摘要。

每条证据使用统一引用结构：

```text
EvidenceReference
- evidenceType
- sourceModule
- recordId
- batchId
- version
- asOf
- summary
```

`AnswerValidator` 检查：

- 事实字段是否能关联工具证据。
- 引用是否来自本次任务返回的数据。
- 是否出现未经证据支持的收益保证、确定性预测或交易承诺。
- 是否泄露 Token、密码、券商会话、完整账户敏感字段或内部密钥。
- 输出是否符合 Research、Diagnostic、Report 或 TradePlan Schema。

## 状态和持久化

一期建议使用 MySQL 保存会话和任务元数据，MongoDB 保存需要引用的新闻、行情和模型事实；不要求新增 Redis。建议表或文档包括：

```text
agent_session
agent_task
agent_tool_call
agent_evidence
agent_report
agent_audit
```

任务状态：

```text
CREATED -> RUNNING -> WAITING_MODEL -> WAITING_TOOL ->
COMPLETED / FAILED / NEEDS_REVIEW / CANCELLED / EXPIRED
```

二期计划状态单独维护，不与任务状态混用：

```text
PENDING_REVALIDATION -> RISK_REJECTED
                     -> EXECUTING -> EXECUTED
                                  \-> FAILED
PENDING_REVALIDATION -> EXPIRED
```

每次工具调用记录工具版本、参数摘要、调用开始/结束时间、结果状态、错误类型和关联证据。参数和结果必须经过脱敏；原始密钥、Cookie、Token 和券商会话不得入库。

所有接口使用 `ResponseDTO<T>` 和明确 DTO，Controller 使用 `@Slf4j` 在入口记录业务日志。建议一期接口如下：

```text

POST /api/agent/tasks/diagnose

```

路径参数放在最后；接口只接受问题、筛选条件、报告日期和任务选项等 DTO，不接受任意工具名、SQL、URL、Bean 名称或方法名。

GET  /api/agent/trade-plans

`revalidate` 只用于系统任务或受控运维触发重新校验，不是人工审批接口，不接受“批准后直接下单”参数。校验通过后由 `tradingExecutor` 内部应用服务创建执行批次并调用 `TradeExecutor`。

## 调度设计

每日投研报告、定期运行诊断和过期任务清理都注册到 `JobConfig + JobSchedulerService`。建议任务名：

```text
agent-daily-research-report
agent-runtime-diagnostic
agent-task-expiration-cleanup
agent-trade-plan-execution
agent-memory-expiration-cleanup
agent-rag-index-maintenance
```

任务默认关闭或仅在用户显式启用后运行。单用户场景不需要 Redis 分布式锁；同一任务的数据库唯一键、运行记录状态和应用内互斥足以防止重复触发。若未来扩展多实例，再增加 Redis 或数据库租约，不把该扩展提前放入一期必需架构。

## 资源控制和降级

- 每次任务限制最大模型轮次、工具调用次数、输入长度、输出长度和总耗时。
- Provider 超时只允许有限次重试；结构化输出失败时不无限重试，转入 `NEEDS_REVIEW`。
- 并发默认 1，队列长度和单日调用次数可配置；超限返回明确的资源不足状态。
- 外部模型不可用时，工具查询和固定诊断仍可执行；无法生成自然语言时返回结构化证据摘要。
- Agent 任务失败不能阻塞 Quartz、策略选股、真实交易或数据库同步任务。自动交易计划失败、拒绝或执行完成必须与 Agent 任务、交易执行批次和券商结果分别留痕。
- 2C4G 部署优先不启动本地大模型；使用外部 Provider 时只保留短上下文和小结果集。

## 与四模块的依赖边界

```text
dataCollector  -> strategyAgent 只读查询
modelService   -> strategyAgent 只读查询
strategyAgent  -> tradingExecutor 输出 TradePlan
tradingExecutor -> strategyAgent 提供 JobExecutionQuery 适配实现
strategyAgent -X-> tradingExecutor 执行服务和 BrokerAdapter 写接口
```

AGENT 可以跨模块聚合证据并决定是否形成交易计划，但不能反向改变源模块事实。对后置模块的运行记录查询通过 `strategyAgent` 内定义的 `JobExecutionQuery` 接口完成，由 `tradingExecutor` 提供适配实现。真实交易仍由：

```text
strategyAgent
  -> TradePlan
tradingExecutor
  -> TradingCalendarService
  -> BrokerReadService / account snapshot
  -> RiskController
  -> TradeExecutor
  -> ZXBrokerAdapter
```

独立完成最终判断。

## 实施顺序

1. 在 `strategyAgent` 内定义 Agent DTO、任务状态、审计模型和 Provider 接口。
2. 建设 Tool Gateway 和四模块只读查询适配器。
3. 实现 Research、Diagnostic、固定模板 Report 和策略对话模式。
4. 增加会话、任务、证据和运行状态接口。
5. 接入 DeepSeek Provider；保留 Ollama 适配器扩展点。
6. 接入统一 JobConfig 调度和失败清理任务。
7. 建立离线问题集，评估工具选择、证据完整率、越权拦截和任务完成率。
8. 建设二期 RAG 摄取、检索和索引维护。
9. 建设 Memory 分层、写入、召回、删除和纠错能力。
10. 评估通过后，由 `strategyAgent` 形成 TradePlan，再由 `tradingExecutor` 自动复核、风控和执行。
