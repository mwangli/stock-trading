# AGENT 六期 RAG 与 Memory 详细设计

## 1. 文档目的

本文档定义股票交易系统中 RAG（Retrieval-Augmented Generation）和 Memory 能力的目标架构、数据采集方式、数据模型、索引策略、检索编排、生命周期管理、权限边界、可观测性和分阶段实施方案。

本文档承接以下既有设计：

- Agent 使用 `strategyAgent` 负责研究、诊断、报告和交易计划草案；`tradingExecutor` 负责实时事实、风险门禁、券商写入和最终执行。
- EmbeddingModel 与 ChatModel 独立配置，当前以 `bge-base-zh-v1.5`、768 维向量和 MongoDB 向量文档为主要基线。
- RAG 和 Memory 结果统一转换为 `EvidenceItem`，必须经过权限、时间有效性、来源状态和向量版本校验。
- 真实行情、账户、持仓、交易日、风控、订单和券商状态只能由结构化业务工具提供，RAG/Memory 不得覆盖实时事实。

本文档不是当前功能已经完成的说明。当前代码已具备基础摄取、基础语义检索、Memory 创建/纠正/遗忘/TTL 和 Embedding 元数据能力；异步数据采集、自动 Memory 候选、混合检索、版本迁移、质量评估和完整审计仍属于本设计的目标实现范围。

## 2. 设计结论

### 2.1 RAG 与 Memory 的职责划分

| 能力 | 解决的问题 | 主要数据 | 是否允许作为交易事实 |
|---|---|---|---|
| RAG | 从受控文档和历史材料中找出与当前问题相关的背景证据 | 新闻、公告、策略说明、模型报告、运维手册、历史复盘 | 否，只能作为背景证据 |
| 短期会话 Memory | 保持当前会话的上下文连续性 | 最近消息、当前任务上下文、用户追问 | 否 |
| 长期 Memory | 保存经过确认的用户偏好、稳定策略习惯和可复用经验 | 用户确认、系统事实、交易结果、人工修正后的记忆 | 否，只能影响研究表达和检索偏好 |
| 结构化业务工具 | 提供实时、可验证、可审计的业务事实 | 行情、候选、模型、日历、资金、持仓、订单、风险门禁 | 是，且交易执行只依赖此类事实 |

### 2.2 目标实现原则

1. 先采集和治理原始数据，再切分、去重、生成向量；禁止把未经来源校验的模型输出直接写入长期 Memory。
2. RAG 文档和 Memory 元数据分离保存，向量只作为可重建索引，不作为唯一事实来源。
3. 所有写入采用内容哈希和来源版本幂等；同一来源重复采集不得产生无界重复 Chunk。
4. 检索采用结构化过滤、关键词候选、向量召回、时间衰减、来源去重和证据状态校验的组合流程。
5. 自动抽取的 Memory 默认进入待确认状态；只有用户确认或满足严格的系统事实规则后，才能进入长期有效记忆。
6. Embedding 模型版本、Provider、维度和状态必须与向量绑定；模型换版后不能混合检索。
7. RAG/Memory 不可用时，研究和诊断可以降级为结构化工具事实；不能用空列表、零值或模型猜测伪装为完整证据。
8. 任何真实交易写入必须重新读取实时事实，并继续经过权限、风控、幂等和执行隔离。

### 3.2 必须补齐的缺口

| 缺口 | 风险 | 目标改进 |
|---|---|---|
| 摄取同步阻塞请求 | 大文档、批量新闻和模型报告会占用接口线程 | 引入采集任务、分阶段状态和可重试批处理 |
| 按字符硬切分 | 可能切断标题、表格、段落和结论 | 采用标题/段落/句子优先的分层切分，并保留父文档关系 |
| 应用层全量余弦排序 | 数据量增大后延迟和内存占用不可控 | 先结构化过滤，再使用向量索引；未具备向量索引时保留受限候选集 |
| PRIVATE 可见范围由请求字段决定 | 前端传入的 `userScope` 不能代表真实授权 | 从认证上下文解析主体和范围，忽略客户端伪造范围 |
| 自动 Memory 无确认队列 | 模型猜测可能被长期保存并污染后续回答 | 增加候选、确认、拒绝、纠正和审计状态 |
| Memory 向量与主记录更新非原子 | 主记录和语义索引可能不一致 | 使用索引状态、补偿任务和一致性对账 |
| 缺少文档撤回与版本切换 | 过时或错误材料仍可能被召回 | 引入文档级状态、版本指针和撤回传播 |
| 缺少召回质量评估 | 无法判断 RAG 是否真的提升回答 | 建立离线查询集、命中率、有效证据率和人工反馈指标 |
| 审计粒度不足 | 无法追踪某个回答引用了什么 | 记录检索请求摘要、候选、最终证据、过滤原因和版本 |

## 4. 总体架构

### 4.1 逻辑分层

1. **Source Adapter 层**：从新闻、公告、策略文档、模型报告、交易复盘、用户对话和系统事件读取原始数据。
2. **Ingestion 层**：负责规范化、去重、敏感信息清洗、来源校验、版本识别、切分和任务状态管理。
3. **Index 层**：负责向量生成、关键词索引、向量索引、索引版本、重建和一致性对账。
4. **Retrieval 层**：负责权限过滤、时间过滤、关键词召回、向量召回、重排、去重、衰减和证据截断。
5. **Evidence 层**：把 RAG、Memory 和结构化工具结果统一转换为 `EvidenceItem`，并标注来源、事实时间、状态和可用性。
6. **Agent Orchestration 层**：按照任务类型选择检索策略，控制上下文预算和证据优先级。
7. **Audit and Feedback 层**：记录采集、索引、检索、确认、纠正、遗忘和用户反馈，为后续评估提供数据。

### 4.2 关键数据流

#### RAG 数据流

原始来源 → 采集任务 → 内容规范化 → 来源校验 → 文档去重 → 分层切分 → Chunk 元数据 → Embedding → 向量索引 → 检索候选 → 权限和时间校验 → 重排 → `EvidenceItem` → Agent 上下文。

#### Memory 数据流

会话消息/用户操作/系统事实/交易结果 → 敏感字段检测 → Memory 候选抽取 → 置信度和稳定性评估 → 用户确认或系统规则确认 → 主记录 → Embedding → 语义索引 → 检索 → `EvidenceItem`。

#### 交易边界数据流

Agent 只能读取并解释 RAG、Memory 和只读工具结果，生成研究结论或交易计划草案。交易执行前由 `tradingExecutor` 重新读取交易日、行情、账户、持仓、订单和风险门禁，任何过期或冲突证据都不能替代实时校验。

## 5. 数据来源与采集设计

### 5.1 RAG 数据源分类

| 来源类型 | 采集对象 | 采集方式 | 更新频率 | 默认有效期 | 信任等级 |
|---|---|---|---|---|---|
| `NEWS` | 新闻标题、摘要、正文、来源、发布时间、关联股票 | 复用现有新闻采集结果，按外部唯一标识增量 | 日内或定时同步 | 7 至 30 天 | 中 |
| `ANNOUNCEMENT` | 公司公告、监管公告、公告摘要 | 复用公告采集结果，按公告编号和版本增量 | 日内同步 | 由公告类型决定 | 高 |
| `STRATEGY_DOC` | 策略说明、参数定义、门禁规则 | 文档导入或受控管理页面 | 发布时 | 版本有效 | 高 |
| `MODEL_REPORT` | 模型版本、评估指标、失败原因、适用范围 | 从模型评估和报告结果生成 | 评估完成时 | 版本有效 | 高 |
| `TRADE_REVIEW` | 已完成交易的复盘摘要和结果 | 从交易结果和人工复盘生成 | 交易终态后 | 90 至 365 天 | 中高 |
| `OPERATIONS` | Agent、Embedding、任务调度和数据质量手册 | 受控文档导入 | 发布时 | 版本有效 | 高 |
| `SYSTEM_EVENT` | 重要系统状态和故障摘要 | 事件归档后生成摘要 | 事件发生后 | 7 至 30 天 | 中 |

不建议把原始行情 K 线、账户全量快照、持仓全量明细和订单明细直接作为 RAG 文档。此类数据应由结构化工具按查询条件实时读取；必要的历史总结可以生成 `MODEL_REPORT` 或 `TRADE_REVIEW`，但必须保留原始数据引用和事实时间。

### 5.2 Memory 数据源分类

| 来源类型 | 可形成的 Memory | 默认处理 |
|---|---|---|
| 用户明确表达 | 用户偏好、研究范围、风险偏好、输出格式偏好 | 可进入待确认或直接确认流程 |
| 用户明确纠正 | 对旧记忆的替换、撤回或补充 | 立即建立纠正关系并使旧版本失效 |
| 系统事实 | 用户选择的策略、已启用的模型和明确配置 | 仅保存非敏感、可追溯、稳定事实 |
| 交易结果 | 已完成交易的结果、复盘标签和收益反馈 | 只保存摘要，不保存凭据和完整账户快照 |
| 模型推断 | 对用户偏好的推测、对话中的隐含结论 | 默认只进入候选，不自动写入长期有效状态 |

### 5.3 采集任务状态

采集任务和索引任务统一使用显式状态：

| 状态 | 含义 | 可重试 |
|---|---|---|
| `CREATED` | 任务已创建但未领取 | 是 |
| `RUNNING` | 正在读取或处理 | 超时后可恢复 |
| `WAITING_EMBEDDING` | 等待 Embedding 就绪 | 是 |
| `PARTIAL` | 部分 Chunk 成功，仍有失败项 | 是 |
| `COMPLETED` | 全部处理成功 | 否，除非人工重建 |
| `FAILED_RETRYABLE` | 外部服务、临时数据库或资源失败 | 是 |
| `FAILED_TERMINAL` | 内容非法、版本冲突或权限错误 | 否，需人工修正 |
| `CANCELLED` | 用户或系统取消 | 否 |

任务必须保存批次标识、来源范围、输入数量、成功数量、跳过数量、失败数量、错误码、开始时间、结束时间和最后处理游标。所有批量任务都必须支持按批次重跑，不能通过删除全量索引后重新导入作为常规恢复手段。

### 5.4 采集与调度规则

1. 新增后台任务必须接入 `JobConfig + JobSchedulerService`，不在业务类新增 `@Scheduled`。
2. 新闻和公告采集应复用已有外部唯一标识、来源时间和内容哈希，避免重新抓取造成重复文档。
3. 模型报告和交易复盘必须在上游业务记录进入稳定状态后再生成 RAG 文档。
4. 采集任务只负责把合格数据交给索引流水线，不在采集线程中执行长时间向量生成。
5. 单批次采用有限大小，失败项单独记录；重试必须使用幂等键，不得重复创建同一文档版本。
6. 数据源为空、解析失败或关键字段缺失时，任务标记失败或部分失败，不能把空响应当作成功采集。

| 字段 | 说明 |

Chunk 是最小检索单元，除现有字段外建议增加：

| 字段 | 说明 |
|---|---|

| `embeddingStatus` | `PENDING`、`READY`、`FAILED`、`STALE` |

| `embeddingModelVersion` | 生成向量的模型版本 |
| `embeddingDimension` | 向量维度 |
| `factTime` | 文本所述事实时间，不等同于采集时间 |
| `expiresAt` | 该 Chunk 的有效期 |
| `active` | 是否允许进入检索候选 |

### 6.3 切分策略

切分顺序如下：

1. 先按文档标题和章节切分，保留 `sectionPath`。
2. 章节过长时按段落切分，避免跨越明显语义边界。
3. 段落仍过长时按句子切分，中文标点和英文句号都作为候选边界。
4. 只有单句仍超过限制时才按有限字符窗口切分，并保留相邻窗口的少量重叠。
5. 标题、股票代码、公告编号、模型版本和结论标签作为元数据，不仅依赖正文语义召回。
6. 表格、列表和结论应尽量作为完整逻辑单元保存；无法保留结构时生成摘要 Chunk，并保留原文引用。

切分长度应以模型 token 估算为主、字符长度为辅，生产参数通过配置管理。每个 Chunk 必须有稳定顺序和可回溯的文档标识，便于回答中展示证据来源和相邻上下文。

## 7. Memory 设计

### 7.1 Memory 分类与优先级

| 类型 | 例子 | 默认 TTL | 默认权重 | 是否需用户确认 |
|---|---|---:|---:|---|
| `PREFERENCE` | 用户偏好的分析语言、摘要粒度、关注行业 | 180 天 | 高 | 建议确认 |
| `SEMANTIC` | 稳定的策略概念、已确认的研究定义 | 365 天 | 中高 | 必须确认或来自受控文档 |
| `EPISODIC` | 某次分析、某次错误和修正过程 | 90 天 | 中 | 建议确认 |
| `TRADING` | 已完成交易复盘摘要、收益反馈和失败原因 | 365 天 | 高 | 系统事实确认 |
| `SESSION` | 当前会话内临时上下文 | 会话结束或 24 小时 | 低 | 不进入长期库 |

### 7.2 Memory 生命周期状态

现有 `ACTIVE`、`CORRECTED`、`FORGOTTEN`、`EXPIRED` 保留，并增加候选状态：

| 状态 | 说明 |
|---|---|
| `CANDIDATE` | 从对话或系统事件抽取，尚未进入长期有效记忆 |
| `PENDING_CONFIRMATION` | 等待用户确认或人工审核 |
| `ACTIVE` | 允许被检索 |
| `CORRECTED` | 被新版本替代，保留历史关系但不参与普通检索 |
| `FORGOTTEN` | 用户主动遗忘或安全策略撤回 |
| `EXPIRED` | 超过 TTL 或事实有效期 |
| `CONFLICTED` | 与同一范围内其他高可信记忆冲突，暂不参与检索 |

### 7.3 自动 Memory 候选规则

只从以下内容提取候选：

- 用户明确使用“以后、默认、我偏好、请记住、不要再”等稳定表达；
- 用户明确纠正 Agent 结论；
- 已完成交易和模型评估结果中的结构化摘要；
- 系统配置中可被用户查看且不包含敏感信息的稳定事实。

以下内容禁止自动写入长期 Memory：

- 单次临时问题、一次性选股结论和未验证的新闻推断；
- API Key、Token、Cookie、密码、私钥、券商会话和完整账户快照；
- 直接由模型生成但没有来源引用的用户画像；
- 交易计划中的预测价格、交易数量、方向和执行状态；
- 从客户端传入但没有认证上下文支持的用户范围。

候选抽取后执行内容清洗、敏感信息扫描、重复检测、冲突检测和置信度分级。低于阈值的候选只保存审计摘要，不进入确认列表；高置信度仍不能绕过交易安全边界。

### 7.4 记忆合并与冲突

同一 `userScope + memoryType + normalizedKey` 下的新记忆不能简单追加。系统应按照以下顺序处理：

1. 内容完全相同：更新最近使用时间和来源计数，不重复创建。
2. 新内容明确纠正旧内容：旧记录转为 `CORRECTED`，新记录建立替代关系。
3. 新旧内容互相冲突但无法判断真伪：两者转为 `CONFLICTED`，提示用户确认。
4. 系统事实与模型推断冲突：系统事实优先，模型推断失效。
5. 用户确认与系统自动推断冲突：用户确认优先，但仍保留来源和更新时间。

## 8. 索引与向量版本管理

### 8.1 索引组成

每个 RAG/Memory 索引由以下维度共同决定：

- Provider；
- 模型版本；
- 向量维度；
- 归一化方式；
- 文本规范化版本；
- 切分策略版本；
- 索引状态。

检索只允许使用与当前运行时完全匹配且状态为 `READY` 的向量。模型版本变化、维度变化、归一化方式变化或切分策略变化，都必须标记旧索引为 `STALE` 并启动重建。

### 8.2 重建流程

1. 注册新 Embedding 版本，状态为 `PREPARING`。
2. 加载模型并完成制品、大小、哈希和维度校验。
3. 按文档版本和 Memory 状态生成新向量，写入新索引版本。
4. 完成数量、失败项、维度、内容哈希和抽样相似度对账。
5. 将新索引标记为 `READY`，再切换默认检索版本。
6. 保留旧版本一段观察期，确认无回滚需要后再清理。

切换不能覆盖旧向量，也不能在同一检索请求中混合不同模型版本。重建失败时继续使用旧的 `READY` 版本，不能把系统状态伪装成 Embedding 可用。

### 8.3 存储策略

当前 MongoDB 文档存储继续保留，分为：

- 文档和 Chunk 元数据集合；
- Memory 向量集合；
- 索引任务和索引版本集合；
- 检索与证据审计集合。

当部署环境明确支持 MongoDB 原生向量索引后，可以替换底层召回实现，但不能改变上层 `RetrievalResult`、`EvidenceItem` 和权限过滤契约。未具备原生向量索引时，应用层计算只能对结构化过滤后的有限候选执行，禁止无界全量扫描。

## 9. 检索编排设计

### 9.1 检索步骤

1. 从认证上下文确定真实 `userScope`、账户范围和权限。
2. 对查询做长度限制、敏感内容检测、股票代码和任务类型识别。
3. 根据任务类型确定允许的来源类型、事实时间范围和最大上下文预算。
4. 先执行结构化过滤：状态、可见性、来源、股票代码、版本、事实时间和 TTL。
5. 执行关键词召回和向量召回，分别保留候选分数。
6. 对候选执行来源版本校验、Embedding 版本校验、过期校验和重复去除。
7. 按相关性、来源可信度、时间新鲜度、用户确认程度和任务适配度重排。
8. 对同一来源只保留有限数量的 Chunk，必要时合并相邻 Chunk。
9. 转换为 `EvidenceItem`，附带证据状态、来源引用和事实时间。
10. 在达到 token、字符和结果数量上限后停止，不把检索结果直接拼接成无界 Prompt。

### 9.2 推荐评分组成

最终排序不使用单一余弦分数，建议由以下因素加权：

- 语义相关性：向量相似度；
- 关键词命中：股票代码、公告编号、模型版本和标题命中；
- 来源可信度：公告和受控策略文档高于模型推断；
- 时间新鲜度：新闻和系统事件按时间衰减，版本化策略文档不按日衰减；
- 用户确认程度：用户确认 Memory 高于模型推断 Memory；
- 任务适配度：研究、诊断、报告和交易计划草案使用不同来源白名单。

权重必须配置化并可审计。权重改变属于检索策略版本变更，应记录到检索审计中，便于比较召回质量。

### 9.3 任务类型检索白名单

| 任务 | 允许的 RAG 来源 | 允许的 Memory | 禁止替代的实时事实 |
|---|---|---|---|
| `RESEARCH` | 新闻、公告、模型报告、策略文档、交易复盘 | 偏好、历史研究和用户确认定义 | 当前价格、账户、持仓 |
| `DIAGNOSTIC` | 运维手册、系统事件、任务记录、模型报告 | 已确认的问题处理偏好 | 当前任务状态必须来自结构化工具 |
| `REPORT` | 版本化报告、历史复盘、公告和模型评估 | 用户输出偏好 | 报告中的当前行情必须实时读取 |
| `TRADE_PLAN` | 策略规则、历史复盘和模型评估 | 用户确认的研究偏好 | 交易日、价格、资金、持仓、风控和订单 |

### 9.4 失败与降级

| 失败情况 | Research/Diagnostic/Report | TradePlan |
|---|---|---|
| Embedding 未就绪 | 降级为关键词或结构化工具，并标记证据不完整 | 不得以 RAG 结果补全缺失事实 |
| MongoDB 不可用 | 返回结构化工具结果和明确降级状态 | 拒绝进入执行链路 |
| 权限过滤异常 | 拒绝返回该候选，不降级为全量数据 | 拒绝生成或标记需人工复核 |
| 版本冲突 | 返回 `UNKNOWN` 或排除候选 | 不得作为执行依据 |
| 全部候选过期 | 返回空证据和过期原因 | 不得生成可执行计划 |

## 10. Evidence 统一契约

RAG、Memory 和结构化工具结果都必须转换为统一证据项，字段至少包括：

| 字段 | 说明 |
|---|---|
| `evidenceId` | 单次任务内唯一标识 |
| `evidenceType` | `RAG`、`MEMORY`、`TOOL` |
| `sourceType` | 新闻、公告、Memory 类型或工具名称 |
| `sourceId` | 来源主键或工具调用标识 |
| `contentSummary` | 脱敏后的证据摘要 |
| `score` | 检索或工具相关性分数 |
| `confidence` | 来源可信度或业务置信度 |
| `factTime` | 证据对应事实时间 |
| `retrievedAt` | 本次召回时间 |
| `status` | `AVAILABLE`、`UNKNOWN`、`EXPIRED`、`REVOKED`、`CONFLICTED` |
| `visibility` | 证据可见范围 |
| `modelVersion` | 生成或引用的模型版本 |
| `citationRef` | 可追溯的来源引用，不保存敏感原文 |

EvidenceAssembler 只允许把 `AVAILABLE` 且通过权限校验的证据放入普通上下文。`UNKNOWN`、`EXPIRED` 和 `CONFLICTED` 可以作为风险提示展示，但不能被模型表达为确定事实。

### 11.1 服务职责

| 服务 | 职责 | 不负责的内容 |
|---|---|---|
| `AgentSourceIngestionService` | 读取来源、规范化、去重、创建采集任务 | 不直接决定交易或写券商 |

| `AgentMemoryCandidateService` | 抽取候选、去重、冲突检测和确认队列 | 不自动保存未经确认的模型推断 |
| `AgentMemoryService` | 长期 Memory 主记录、纠正、遗忘、TTL 和向量同步 | 不读取券商凭据 |

### 11.2 接口操作清单

接口仍统一使用 `ResponseDTO<T>`，请求和响应使用独立 DTO。逻辑操作包括：

| 操作 | 请求重点 | 响应重点 |
|---|---|---|
| 创建采集任务 | 来源类型、来源范围、版本和幂等键 | 任务标识、状态和批次范围 |
| 查询采集任务 | 任务标识或批次 | 状态、计数、失败摘要和游标 |
| 重试失败项 | 任务标识、失败项范围 | 新批次标识和可重试数量 |
| 撤回文档 | 文档标识、撤回原因 | 文档状态和传播状态 |
| 查询 RAG | 查询、任务类型、股票范围和时间范围 | Evidence 列表、降级状态和版本 |
| 创建 Memory 候选 | 来源、类型、内容摘要和置信度 | 候选标识和确认状态 |
| 确认/拒绝候选 | 候选标识、操作原因 | 长期 Memory 标识和状态 |
| 纠正 Memory | 记忆标识、修正内容和来源 | 新旧版本关系和状态 |
| 遗忘 Memory | 记忆标识、遗忘原因 | 失效状态和索引同步状态 |
| 查询 Memory | 真实用户范围、类型和状态 | 脱敏后的记忆摘要 |
| 查询索引状态 | 索引类型和模型版本 | READY、重建、失败和对账结果 |

客户端不得把 `userScope` 当作授权凭据。服务端应从认证上下文解析主体和范围，传入字段只允许作为查询过滤的附加条件，并且只能缩小范围。

## 12. 数据一致性与幂等

### 12.1 RAG 幂等键

RAG 文档的幂等键由 `sourceType + sourceId + sourceVersion + contentHash` 组成。Chunk 的稳定标识还需包含 Chunk 顺序和切分策略版本。相同来源版本内容未变化时不重新生成向量；内容变化时创建新版本并使旧版本进入 `SUPERSEDED`。

### 12.2 Memory 一致性

MySQL 主记录成功而 Mongo 向量失败时：

- 主记录保持 `ACTIVE` 或 `PENDING_INDEX`，但不允许语义检索使用；
- 索引任务记录失败原因和重试次数；
- 补偿任务根据 Memory 内容哈希重新生成向量；
- 超过重试上限时标记 `INDEX_FAILED`，在运行状态中展示未就绪，不删除主记录。

Mongo 向量存在而主记录已经遗忘、过期或撤回时，检索阶段必须以主记录状态为准；对账任务负责异步将向量置为 inactive。

### 12.3 文档撤回传播

文档撤回必须传播到所有 Chunk、向量索引、缓存和证据审计引用。历史审计可以保留“曾经引用过”的摘要，但新请求不得再返回已撤回内容。若撤回原因涉及安全或敏感信息，缓存和派生摘要也必须进入清理任务。

## 13. 安全、权限与隐私

1. API Key、Token、Cookie、密码、私钥和券商会话只允许存在运行环境或安全配置，不进入 RAG、Memory、日志和 Evidence。
2. 文档可见范围至少区分公共、账户、用户和私有；检索必须先授权过滤，再做语义排序。
3. 股票代码不等于权限范围，不能因为查询包含某股票代码就返回该股票的所有私人材料。
4. 记录日志时只保存查询摘要、哈希、长度、来源类型和结果状态；不保存完整 Prompt、完整账户快照和原始敏感文本。
5. 前端只展示 Provider、模型版本、索引状态、证据来源和脱敏摘要，不展示密钥、内部存储路径和未授权范围。
6. 交易相关的 RAG/Memory 只能产生研究背景、风险提示和解释，不得直接决定方向、数量、金额、执行状态或券商调用。
7. 权限过滤异常必须失败关闭，不得为了返回结果而扩大到全量范围。
8. 用户遗忘操作应优先级高于普通 TTL，且需要记录操作主体、时间、原因和传播结果。

## 14. 可观测性与质量评估

### 14.1 采集指标

- 各来源每日输入文档数、去重数、跳过数和失败数；
- 文档到 Chunk 的平均膨胀比例；
- Embedding 成功率、平均耗时、P95 耗时和失败错误码；
- 版本重建耗时、剩余数量和失败项数量；
- 主记录与向量索引不一致数量；
- 撤回文档的传播完成时间。

### 14.2 检索指标

- 查询总量、按任务类型和来源类型分布；
- P50/P95 检索耗时；
- 空结果率、降级率、权限过滤拒绝率和过期证据率；
- Top-K 命中率、来源覆盖率和重复率；
- 用户打开证据、引用证据、纠正答案和标记无关的比例；
- 证据进入上下文后的回答完成率和人工有效率。

### 14.3 离线评估集

建立按任务类型分组的固定查询集，每条查询包含：问题、授权范围、期望来源、期望文档/Chunk、禁止引用的来源、事实时间和可接受答案边界。

最低评估指标：

| 指标 | 含义 | 建议门槛 |
|---|---|---:|
| Recall@K | 期望证据是否出现在前 K 个候选中 | 研究和诊断分别统计 |
| Precision@K | 前 K 个候选中有效证据比例 | 不低于基线 |
| MRR | 第一条有效证据的排序位置 | 持续提升 |
| Freshness Rate | 返回证据仍处于有效时间范围的比例 | 关键来源接近 100% |
| Permission Leakage | 越权返回数量 | 必须为 0 |
| Citation Coverage | 回答中可追溯结论的证据覆盖率 | 关键结论必须有来源 |
| Memory Correction Rate | 用户纠正长期 Memory 的比例 | 作为污染监测指标 |

## 15. 前端与运维展示

### 15.1 Agent 工作台

工作台只展示必要的能力状态：

- RAG：是否启用、索引是否 READY、当前模型版本和最近一次失败摘要；
- Memory：会话 Memory、长期 Memory 和待确认候选数量；
- Evidence：来源类型、事实时间、证据状态、引用摘要和版本；
- Degraded：明确说明是 Embedding 未就绪、数据过期、权限过滤或模型 Provider 问题。

不新增常驻告警横幅；状态应就近通过 Tag、统计项、证据状态和操作结果 Toast 表达。普通页面保持单一纵向滚动容器，证据详情、日志和确认面板可以使用有界内部滚动。

### 15.2 运维页面

运维视图至少包含：

- 采集任务列表、批次进度、失败项和重试入口；
- 文档版本和撤回状态；
- Embedding 当前版本、向量维度、READY 状态和重建进度；
- Memory 候选确认队列、冲突列表、过期和遗忘记录；
- 检索延迟、空结果率、权限拒绝和引用覆盖率；
- 不能展示密钥、原始敏感内容和未授权文档正文。

## 16. 分阶段实施计划

### 阶段一：采集与文档治理

- 增加来源适配器和采集任务状态；
- 实现内容规范化、哈希去重、文档版本和撤回状态；
- 将同步摄取改造成任务化批处理；
- 完成新闻、公告、策略文档和模型报告四类来源；
- 增加采集任务和文档状态的静态审计字段。

### 阶段二：索引和检索重构

- 引入分层切分和 Chunk 父子关系；
- 增加索引版本、切分策略版本和重建任务；
- 限制应用层余弦计算的候选规模；
- 实现关键词与向量混合召回、来源去重和时间衰减；
- 统一转换为 `EvidenceItem` 并接入现有 EvidenceAssembler。

### 阶段三：Memory 候选和治理

- 增加候选、待确认、冲突和索引失败状态；
- 实现对话、系统事实和交易结果的受控候选抽取；
- 增加确认、拒绝、纠正、遗忘和替代关系；
- 将认证范围作为唯一授权来源；
- 增加主记录与向量索引对账和补偿任务。

### 阶段四：质量评估和运维闭环

- 建立离线查询集和基准指标；
- 增加检索反馈和证据引用统计；
- 建立 Embedding 换版双索引、回滚和观察期；
- 增加前端索引状态、采集任务和 Memory 确认工作台；
- 完成安全审计、越权测试设计和数据保留策略。

### 阶段五：受控生产启用

- 先启用研究和诊断任务；
- 再启用报告任务；
- 交易计划只允许读取 RAG/Memory 背景证据，实时事实仍由结构化工具提供；
- 观察期内禁止 RAG/Memory 直接改变交易执行门禁；
- 只有在权限泄漏为零、索引一致性达标、关键查询集通过和审计字段完整后，才扩大使用范围。

## 17. 任务拆分与验收标准

| 任务 | 目标 | 主要验收标准 |
|---|---|---|
| RAG-01 | 采集任务和来源适配器 | 相同来源版本重复提交不会产生重复文档；失败项可按批次重试 |
| RAG-02 | 文档版本和撤回 | 文档撤回后新检索不返回其 Chunk；历史审计保留脱敏引用 |
| RAG-03 | 分层切分 | 标题、章节、段落和 Chunk 顺序可回溯；切分策略版本可识别 |
| RAG-04 | 向量索引版本 | 检索只使用 READY 且 Provider、模型版本、维度一致的向量 |
| RAG-05 | 混合检索 | 结构化过滤先于排序；权限过滤异常时不返回全量候选 |
| MEM-01 | Memory 候选 | 模型推断默认进入候选，不直接进入长期 ACTIVE |
| MEM-02 | 确认和纠正 | 用户确认、拒绝、纠正和遗忘均有状态变化和审计记录 |
| MEM-03 | 一致性补偿 | 主记录和向量索引不一致时可检测、可重试、可恢复 |
| EVD-01 | Evidence 统一 | RAG、Memory 和工具结果都能标识来源、事实时间、状态和引用 |
| SEC-01 | 权限隔离 | 客户端伪造 `userScope` 不能扩大可见范围；越权返回为零 |
| SEC-02 | 敏感信息 | 密钥、Token、Cookie、密码、私钥和完整账户快照不会进入长期数据或日志 |
| OBS-01 | 质量指标 | 能按任务类型查看空结果、降级、延迟、有效证据和引用覆盖率 |
| OPS-01 | 调度边界 | 后台任务全部通过统一调度中心注册，不新增业务类 `@Scheduled` |

## 18. 静态验证边界

本设计完成后的第一轮验证只包括：

- 文档与现有五期设计的边界一致性检查；
- 对现有 RAG、Memory、Embedding、Evidence 和 Agent 调用方的源码定向检索；
- DTO、服务职责、数据状态和配置命名的静态核对；
