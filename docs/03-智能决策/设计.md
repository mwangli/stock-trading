# 03-智能决策设计

## 组件边界

```text
modelService 预测批次 + dataCollector 行情/新闻
             -> StrategyScheduler / StockSelector
             -> ScoreCalculator / DecisionAggregator
             -> 可成交性过滤 + 策略状态
             -> TradingSignal / StockRanking
             -> StrategyAgent 综合证据并形成 TradePlan
             -> tradingExecutor 重新读取并执行门禁
```

- `StockSelector` 负责股票池和候选筛选。
- `ScoreCalculator` 负责模型、情感和行情特征的归一化与加权。
- `DecisionAggregator` 负责合并信号、稳定排序和失效原因。
- `BacktestEngine` 只读历史数据，输出回测运行和交易明细，不复用真实订单实体。
- `StrategyStateManager` 维护策略模式和切换审计；策略状态不是交易执行状态。
- `StrategyAgent` 负责会话、工具调用、RAG、Memory、策略解释、运行诊断和交易计划决策。
- Agent 只能生成 `TradePlan`，不能依赖 `TradeExecutor`、`BrokerAdapter` 或交易执行实体；交易计划执行服务属于 `tradingExecutor`。

## 数据与状态

候选、排名、信号和回测记录写入现有持久化层；计算过程中的临时集合只保存在方法作用域。禁止用缓存中的候选直接代表当前可下单状态，交易执行前必须重新读取账户、行情、交易日历和风险状态。

StrategyRuntimeState 使用 MySQL 单行保存策略总开关、当前模式、禁用指标、自动切换开关和最近切换时间。StrategyStateManager 更新时使用悲观写锁串行化同一状态行，多实例共享数据库事实；SwitchLog 继续保存每次模式切换审计。Flyway V17 创建状态表并写入默认行，避免应用启动阶段并发初始化。

StockSelector 不再对全市场临时重复执行 LSTM 推理，而是通过模型服务读取目标交易日最新的 COMPLETED、PARTIAL 或 EVALUATED 预测批次。读取时校验预测明细数量与批次成功数一致，并拒绝缺少收益、方向概率或下行风险的明细。候选快照写入 candidateBatchId、predictionBatchId、两个模型版本、策略配置版本、基准日、目标日和信息截止时间。

建议状态：

```text
GENERATED -> ELIGIBLE -> EXPIRED
          \-> REJECTED
```

状态转换必须记录模型版本、行情基准日、目标交易日、操作者/任务来源和原因。已过期候选不得通过更新字段重新变成可执行候选。

## 调度与接口

策略任务和 Agent 报告任务由 `tradingExecutor.job` 中的固定 Quartz Job 触发，智能决策模块只暴露无参业务 Job 方法和查询服务，不在业务类使用 `@Scheduled`。对外接口使用明确 DTO 和 `ResponseDTO<T>`，不暴露 Entity 或 `Map`。前端策略页面增加 Agent 对话区域，调用智能决策接口。

## 回测设计

- 回测运行保存策略版本、数据范围、模型版本、费用参数、滑点参数和运行时间。
- 每个交易日只读取当日及之前已存在的事实数据，下一交易日成交价使用下一根可成交行情。
- 回测成交、持仓和收益只写回测实体；真实账户数据由 `tradingExecutor` 独立维护。
- 缺行情、停牌、涨跌停和数据校验失败必须形成可统计的跳过原因，不静默丢弃。

## 失败与降级

- 单只股票输入不完整：该股票标记为不可用并保留原因。
- 全市场预测批次不可用：本次选股失败，不生成可执行候选。
- 预测批次统计与明细数量不一致：整批拒绝，不从残缺数据生成候选。
- 情感结果缺失：按业务配置拒绝该股票或拒绝整批，不能默认补零。
- 券商状态不可用：由交易执行模块拒绝委托，策略模块不模拟成功。

## 可简化设计

- 先保留单一综合评分公式和一个策略模式，不引入规则 DSL。
- 先保留单实例内存计算，不引入 Redis；需要恢复的数据写入现有 MySQL/MongoDB。
- 回测先支持日线和固定费用参数，分钟级撮合只在真实需求明确后扩展。

## 策略配置页面设计

### 页面信息架构

新增独立路由 `/strategyConfig`，页面分为四个区域：策略状态摘要、模式选择、选股与技术指标参数、最近选股排名。系统设置页面不嵌入策略表单，只增加导航入口或说明链接。

### 后端接口设计

保留 `/api/strategy/config` 作为配置读写入口，但控制器不再直接暴露 JPA Entity，统一使用 `StrategyConfigDto`。DTO 显式包含模式、权重、数量、阈值和四类指标开关字段。

`StrategyConfigService` 负责 DTO 与 Entity 转换、默认值补齐和业务校验：LSTM 与情感权重之和必须为 1；权重和阈值必须为有限数；`topN` 限制在 1 至 100；综合得分限制在 0 至 1；收益退出阈值按高收益不低于正常收益、正常收益不低于低收益、低收益不低于亏损阈值校验。

页面通过 `/api/strategy/state` 获取运行状态，通过 `/api/strategy/rankings` 获取最近排名。保存配置后重新读取配置和状态，确保界面展示的是后端持久化结果，而不是仅保留前端表单状态。

### Agent 对话实现意图

策略配置页在现有策略状态、模式、指标和排名区域旁增加 Agent 对话区域。对话请求必须带会话标识和用户问题，响应展示结论、证据、数据截止时间和不确定性。生成交易计划时展示计划状态和风险复核结果，不把 Agent 输出直接渲染成可下单参数。

### 前端实现意图

新增 `StrategyConfig.tsx`，使用 Ant Design `Form`、`Card`、`Select`、`InputNumber` 和 `Switch` 构建参数表单；使用统一的 `request` 客户端访问接口，所有表单字段采用明确 TypeScript 类型。模式切换使用预设配置填充表单，保存操作统一调用配置接口。

参数区按业务含义分组，权重使用 0 至 1 数值输入，百分比阈值在页面显示业务单位但提交时保持后端既有数值契约。页面不对保存按钮增加不可逆禁用门禁，只在提交期间显示加载状态；后端返回错误时保留用户输入并提示具体原因。

## 多策略评估设计

### 评估对象和数据绑定

`StrategyEvaluationService` 以策略模式和不可变配置版本为评估对象，读取最近一年候选排名，并按候选保存的预测批次和股票代码关联 `model_predictions` 的实际收益。候选按批次等权聚合为日收益序列，避免候选数量变化直接放大某日权重。每次结果保存模式、配置版本、起止日期、批次数、候选数、关联完整率和样本充分性。

### 指标计算与决策门禁

评估按时间顺序将最后 30% 候选批次作为样本外区间，计算复合净收益、最大回撤、胜率、盈亏比和稳定性。窗口至少需要 20 个候选批次、100 条候选、5 个样本外批次，且候选与实际收益的匹配率不低于 95%；任一条件不满足时状态为 `INSUFFICIENT_DATA`，指标保持空值而不是显示为零。结果写入 `strategy_evaluation`，页面读取最近结果，不在查询时重复计算。

`StrategyEvaluationJob` 由 `StrategyEvaluationQuartzJob` 接入统一调度中心，任务名为 `strategy-evaluation`，默认关闭。评估结果当前只提供观察和人工决策依据，不参与 `StrategySwitcher` 的自动规则，也不触发配置发布或真实交易。

### 切换状态和审计

`StrategyStateManager` 保存当前模式、策略总开关、自动切换开关、最近切换时间和最近自动切换时间；`SwitchLog` 保存 `SwitchType`、触发来源、操作者、原模式、目标模式、原因和时间。`StrategyModeManager` 负责应用预设配置并形成新版本，`StrategySwitcher` 只负责规则判断和切换门禁，不直接处理交易。

`StrategyConfigService` 的页面保存、重置和模式切换都插入新的配置记录，不更新历史版本。候选保存配置版本后，可通过版本号还原当时权重、阈值和候选数量，避免评估被当前配置反向改写。

自动切换通过 `StrategyAutoSwitchJob` 和 `StrategyAutoSwitchQuartzJob` 接入统一 `JobConfig + JobSchedulerService`。任务从 `ModelReferenceDailyBar` 读取同一市场序列最近两个有效收盘价，计算市场涨跌幅后交给 `StrategySwitcher`。市场参考序列不足、收盘价无效或自动切换未开启时保持原状态并记录日志。数据库迁移新增 `strategy-auto-switch` 任务，初始状态为关闭；策略页的 `/api/strategy/autoSwitch` 接口同时更新运行状态和 Quartz 任务状态，重启后以数据库任务状态为准。

### 规则与保护参数

第一阶段规则采用固定阈值，便于解释和回溯：市场跌幅不低于 5 个百分点时建议保守，涨幅不低于 3 个百分点时建议激进，其他正常状态建议均衡。切换前检查当前模式是否已经是目标模式，以及最近一次状态变更是否仍在 24 小时冷却期。人工切换沿用同一状态记录，因此人工操作也能阻止自动规则立即覆盖。

## 自动调整设计

自动调整不直接修改当前配置。后续新增的 `StrategyAdjustmentCandidate` 保存基准配置、候选配置、触发窗口、调整字段、变化幅度、预期收益、回测结果和发布状态。候选生成必须满足最小样本量、连续两个以上窗口恶化、数据质量通过和回测无未来数据四项门禁；权重单次变化建议不超过 0.05，`topN` 和最低分数限制在业务允许范围内。

候选配置先进入 `PENDING_REVIEW`，通过独立回测后进入 `READY`，由人工或明确发布任务切换为 `ACTIVE`。任何新配置均可回滚到上一稳定版本。第一阶段不做自由搜索、强化学习或基于单日收益的在线调参，避免将噪声放大为策略行为。

## 页面扩展设计

策略配置页增加“策略评估与切换”和“Agent 对话”区域，展示当前模式卡片、模式评估对比表、自动切换开关、冷却剩余时间、最近切换原因、切换历史、Agent 结论和证据。评估数据为空时显示“尚无可用评估结果”及原因，不以空表或零值代替。自动调整候选单独展示为待审核列表，不与当前生效配置混在同一表单中。
