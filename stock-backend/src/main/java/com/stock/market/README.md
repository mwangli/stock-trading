# Market 市场事实模块

## 模块定位

`com.stock.market` 是 Backend 的市场事实数据边界，负责股票资料、行情、新闻、交易日历、复权因子、参考序列、历史股票池和每日可交易状态的采集、标准化、持久化与只读查询。

本模块提供事实，不负责模型推断、策略决策或真实交易执行。外部数据源为空、解析失败或覆盖范围不明确时必须明确失败，不能把不完整数据伪装为成功结果。

## 核心能力

| 能力 | 主要职责 |
|---|---|
| 股票资料 | 全量同步代码、名称、市场、行业、上市和退市信息 |
| 行情 | 日线增量、历史回补、分钟数据、覆盖统计和查询 |
| 交易日历 | 开闭市状态、节假日、覆盖范围和确认状态 |
| 模型数据基础 | 复权因子、参考指数、历史股票池和每日可交易事实 |
| 新闻 | 采集、标准化、去重、分类和事件事实沉淀 |
| 数据质量 | 区分缺失、过期、解析失败、来源不可用和覆盖不足 |

## 重点能力详细设计

### 1. 股票资料全量同步与退市治理

**设计目标**：使用一次外部全量快照完成股票资料对账，避免主循环逐条查询数据库，并防止将接口短暂漏数误判为退市。

处理流程：

1. `StockListSyncService` 先通过 `SecuritiesClient` 获取完整股票列表；响应为空直接失败。
2. `StockDataParser` 解析并按股票代码去重，代码为空的记录不进入同步计划。
3. 一次性读取数据库现有股票资料，按代码划分为更新、新增和数据库独有三组。
4. 更新组只覆盖外部源明确返回的字段，保留本地已有但本次缺失的信息。
5. 新增组仅对缺少上市日期的股票补查上市日期，再按固定批次写入。
6. 数据库独有组只有在名称、证券类别或市场说明中存在明确退市语义时，才调用关联清理服务；其余记录保留并计入忽略数。

关键结果包括外部总数、新增数、更新数、已清理退市数、忽略缺失数、失败数和耗时。写入成功后清理股票资料缓存，避免读取旧列表。

失败语义：外部列表为空、解析后无有效代码或批量持久化异常均不得返回“同步成功”；退市证据不足只记为忽略，不执行删除。

### 2. 行情增量同步与历史回补

**设计目标**：把当日可用性与长期完整性拆开治理，避免历史缺口拖垮日常行情链路。

- `StockPriceService.syncDailyPrice` 面向单股票、单交易日增量同步，适合日常任务组合调用。
- `StockPriceService.backfillHistoricalPrices` 面向明确日期范围的历史补齐，独立统计获取、解析、写入和缺失情况。
- 行情记录按股票代码和交易日期形成稳定事实，重复同步应更新同一业务记录而不是制造重复数据。
- 外部请求、响应解析和持久化分别归入 `client`、`parser`、`service/repository`，供应商格式不能扩散到上游模块。
- 批量同步需要保留成功、跳过和失败原因；某只股票失败不能被空集合或默认值掩盖。

日常增量只处理当前任务要求的交易窗口；大跨度补数、数据修复和重新计算由独立回补任务执行。二者拥有不同的运行记录和失败恢复入口。

### 3. 交易日历确认与滚动维护

**设计目标**：向模型、决策和执行模块提供“已确认的交易日事实”，禁止使用周一至周五的简单判断代替证券市场日历。

`TradingCalendarService` 负责查询和强制校验。需要真实业务动作时调用强校验接口；目标日期没有确认记录或被标记为休市时，训练、预测、选股和自动交易应跳过或失败。

`TradingCalendarMaintenanceService` 负责按时间窗口补齐和滚动维护日历覆盖：

1. 计算当前已有覆盖范围和目标维护范围。
2. 通过 `TradingCalendarSourceClient` 获取外部日历。
3. 标准化交易日、休市日、来源和确认状态。
4. 批量持久化并返回覆盖结果。

外部日历不可用时，不允许自动回退为“工作日即交易日”。调用方必须看到未确认状态，从而阻断对时点敏感的业务。

### 4. 新闻采集、标准化与事件事实

**设计目标**：同时保留原始证据和可计算的标准化事实，让情感模型与策略可以追溯输入来源。

在线处理由 `NewsCollectionPipelineService` 编排，主要步骤为内容清洗、来源与时间标准化、文档类型识别、角色分类、质量状态判断和管线版本记录。新闻原文、标题、摘要、来源、发布时间和内容哈希属于基础事实；情感标签和事件分类属于派生结果，不能覆盖原始证据。

`NewsEventFactService` 将符合条件的文档转换为事件事实，并使用稳定标识抑制重复事件。重复文档、忽略文档和质量不足文档分别计数，不能统一当作成功事件。

历史治理由 `NewsCollectionBackfillService` 完成：

- 以管线版本作为回填状态主键。
- 按 MongoDB `_id` 升序游标分批读取，仅处理管线版本过期或质量状态未就绪的数据。
- 每批先运行与在线路径相同的处理管线，再保存新闻和事件事实。
- 每个成功批次持久化最后处理 ID、累计计数和类型分布。
- 达到单次最大处理量后回到 `PENDING`，下次从已保存游标继续。
- 发生异常时标记 `FAILED` 并保留最后成功游标，禁止从头重复回填。

### 5. 模型数据基础与跨模块查询

复权因子、参考指数、历史股票池、每日可交易状态和标准行情共同构成模型与回测的数据基础。`MarketDataFoundationService` 负责这些事实的导入或维护，数据必须携带业务日期、来源和版本信息。

`MarketDataQueryService` 是跨模块只读入口：

- 将内部 Entity 转换为稳定 DTO。
- 提供按股票、日期、时间窗口和信息截止时间查询的能力。
- 对缺失、覆盖不足和数据过期返回明确结果，不伪造补零数据。
- `model`、`decision`、`execution` 和 `platform` 只能通过公开 Service/DTO 读取市场事实。

### 6. 数据质量审计

`BacktestDataAuditService` 等质量服务在数据进入训练、回测或决策前检查覆盖范围、时间连续性、股票池有效性和关键信息缺失。质量结果至少区分：

| 状态 | 含义 | 处理要求 |
|---|---|---|
| 缺失 | 目标事实不存在 | 阻断依赖该事实的计算或明确跳过 |
| 过期 | 数据存在但不满足时效 | 不得作为实时交易依据 |
| 解析失败 | 已取得响应但无法形成可信记录 | 记录来源和解析错误并失败 |
| 来源不可用 | 外部服务不可达或拒绝请求 | 保留原有事实，不写入空结果 |
| 覆盖不足 | 有部分数据但未达到业务门槛 | 返回覆盖率和缺口，不伪装完整 |

审计只判断数据是否满足用途，不在本模块内执行模型训练、策略评分或交易放行。

## 数据与对外边界

- 市场 Repository 和 Entity 只在本模块内部使用。
- `MarketDataQueryService` 将市场持久化对象转换为明确 DTO，供 `model`、`decision`、`execution` 和 `platform` 读取。
- 上游模块不得直接引用 `com.stock.market.repository` 或 `com.stock.market.entity`。
- Agent 只能通过 `platform` 提供的内部事实 API 获取最小、只读、脱敏摘要。
- Redis 仅用于可重建缓存，权威事实仍以持久化数据为准。

### 目标与非目标

本专项将新闻质量治理前移到采集层。证券数据源返回的每条文档必须在持久化阶段完成原始内容留存、规范化、文档类型识别、业务角色识别、内容去重和事件事实同步。情感模型、选股和后续时序模型只消费版本化事件事实，不再各自清洗原始新闻。

本方案不删除原始文档，不把证券平台菜单编号直接解释为真实文档类型，不在数据治理阶段自动激活模型，也不承诺清洗一定改善收益。模型升级必须等待本专项的数据 Gate 取得运行证据。

### 当前数据证据

2026-10-23 对 `stock_news` 进行只读抽样时，集合约有 51.09 万条记录，其中约 97.67% 缺少完整事件元数据。来源高度集中，栏目“新闻”中大量记录实为交易所公告，栏目“公告”中又包含评级和行业研究内容。2,400 条标题样本的规范化重复率约为 16.08%。

历史 `stockRanking` 样本中的旧 `sentimentScore` 均值约为 0.99812，标准差约为 0.000861，不能证明新闻因子提供了有效横截面区分。当前源码虽已过滤非 `actionable` 结果，但新逻辑尚无回填、训练或实际选股评估证据。

### 采集链路与类职责

```text
证券数据源
  → 原始响应解析
  → 标题和正文规范化
  → 文档类型识别
  → 业务角色识别
  → 内容摘要与规范事件标识生成
  → stock_news 原始文档写入
  → stock_news_event_facts 幂等聚合
```

- `StockNewsDocumentFactory` 只负责请求详情并构造原始文档。
- `NewsDocumentNormalizer` 负责 HTML、URL、重复股票前缀、页眉页脚、免责声明和空白规范化。
- `NewsDocumentClassifier` 根据来源、标题和正文推导文档类型，不依赖菜单显示名称。
- `NewsDocumentRoleResolver` 将文档划分为 `TRADE_SIGNAL`、`RISK_ONLY`、`CONTEXT_ONLY` 或 `IGNORE`。
- `NewsCanonicalEventResolver` 生成规范化内容摘要和跨来源事件标识。
- `NewsCollectionPipelineService` 统一编排规则并写回治理字段。
- `NewsEventFactService` 将非 `IGNORE` 文档幂等聚合到事件事实集合。

### `stock_news` 原始文档契约

`stock_news` 保留原有 `title` 和 `content`，并维护以下治理字段：

| 字段 | 含义 |
|---|---|
| `rawMenuId` | 供应商菜单编号，仅用于来源追踪 |
| `rawTitle` / `rawContent` | 供应商原始标题和正文 |
| `normalizedTitle` / `normalizedContent` | 采集层规范化结果 |
| `sourceChannel` | 原始渠道名称，不承担业务类型语义 |
| `documentType` | 真实文档类型 |
| `documentRole` | 下游业务角色 |
| `contentHash` | 规范化标题和正文摘要 |
| `canonicalEventId` | 规范事件标识 |
| `noveltyScore` | 新颖度，范围 `[0,1]` |
| `materialityScore` | 重要性，范围 `[0,1]` |
| `stockSpecificity` | 股票相关度，范围 `[0,1]` |
| `pipelineVersion` | 采集治理规则版本 |
| `qualityStatus` / `qualityReason` | 质量状态和原因 |

菜单编号只写入 `rawMenuId`。既有 `category` 作为兼容展示字段保留，不再作为公告半衰期、模型权重或真实文档类型依据。

### 文档类型与业务角色

文档类型固定为 `OFFICIAL_DISCLOSURE`、`MEDIA_NEWS`、`RESEARCH_REPORT`、`RATING_CHANGE`、`INVESTOR_QA` 和 `UNKNOWN`。

| 业务角色 | 下游用途 |
|---|---|
| `TRADE_SIGNAL` | 可进入情感推理和模型特征 |
| `RISK_ONLY` | 进入 Java 风险门禁，不与正向 Alpha 抵消 |
| `CONTEXT_ONLY` | 保留研究和审计，不参与选股评分 |
| `IGNORE` | 空内容、模板噪声或无有效语义，不生成事件事实 |

董事会和监事会例行决议、制度修订、独立董事声明等默认属于 `CONTEXT_ONLY`。只有包含明确增减持、回购、控制权变化、重大合同、业绩变化、监管处罚或诉讼事实时，才能提升为可交易角色。

### `stock_news_event_facts` 事件事实契约

交易事件事实以 `(stockCode, canonicalEventId)` 唯一，仅保存 `TRADE_SIGNAL` 和 `RISK_ONLY` 的规范化文本、文档类型、业务角色、事件类型、发布时间、来源集合、外部文档标识集合、重要性和采集管线版本。`CONTEXT_ONLY` 保留在原始新闻治理字段中供研究查询，不再向交易事件事实集合重复保存完整正文。

重复文档只补充来源和外部标识，不重复形成情感权重。事件事实保留最早发布时间和最晚观察时间，历史乱序回填不能覆盖点时边界。相同 `canonicalEventId` 可以关联不同股票，但每只股票保留独立事实。

情感训练和新闻排名只消费 `TRADE_SIGNAL`；`RISK_ONLY` 只进入独立 Java 风险门禁；`CONTEXT_ONLY` 不生成交易事件事实。没有事件事实与存在中性事件必须分别表达，不能统一编码为固定 `0.5`。`NEWS_EVENT_RANKING_ENABLED` 与 `NEWS_EVENT_RISK_GATE_ENABLED` 默认均为 `false`，对应收益 Gate 或风险 Gate 取得证据后才能分别开启。

### 历史回填设计

历史回填复用 `NewsCollectionPipelineService`，通过 MongoDB `_id` 游标升序处理，并持久化 `pipelineVersion`、最后游标、扫描数、更新数、新增事实数、重复数、文档类型分布、业务角色分布、忽略数和失败数。

只有一批原始文档和对应事件事实都持久化成功后才能推进游标。达到单次最大处理量后状态回到 `PENDING`，下次从已保存游标继续；异常时标记 `FAILED` 并保留最后成功游标。

任务通过 `JobConfig + JobSchedulerService` 注册且默认暂停，防止未完成容量验证时在 2C4G 节点自动扫描约 51 万条文档，不新增 `@Scheduled`。

### `NEWS_COLLECTION_V5` 规则与验证

2026-10-24 对 `stock_news` 执行两阶段验证：先按 `_id` 读取最早和最新各 1,200 条进行只读规则迭代，再对最早和最新各 5,000 条执行隔离影子回填。生产 `stock_news` 和生产 `stock_news_event_facts` 均未修改。

V1 至 V3 完成 HTML、URL、重复前缀和免责声明清理，纠正菜单栏目与真实文档类型错位，并加入例行公告、行情播报和硬风险分流。V3 的 2,400 条抽样结果为 `RISK_ONLY` 8 条、`TRADE_SIGNAL` 380 条、`CONTEXT_ONLY` 1,896 条、`IGNORE` 116 条。

10,000 条 V3 影子回填暴露两个生产问题：同一规范事件存在 12 组跨来源角色冲突；清洗文档和事件事实同时保存完整正文，全量存储与索引外推约增加 7.59GB。

V4/V5 继续完成以下收敛：

- 标题当前事实优先于正文历史描述，避免长正文中的解除、否定或模板语义覆盖当前风险事件。
- 业绩预盈、预亏、预增、预减，中标候选，股票质押式回购，以及诉讼仲裁进展加入明确标题规则。
- 解除司法冻结、解除冻结、解冻和解除质押优先作为解除事件；同时包含新增、补充、轮候或再次质押时仍按当前风险处理。
- 通用投资者关系和调研活动标题加入正文指纹，避免同一十日桶内不同活动被错误合并。
- 事件事实只保存 `TRADE_SIGNAL` 和 `RISK_ONLY`；`CONTEXT_ONLY` 只保留治理元数据和原始文档引用。
- 同批事件先聚合后无序 bulk upsert，并保留 `observedDocumentRoles` 供跨来源审计。

相同 10,000 条 V5 影子回填结果：治理字段完整率 100%，`RISK_ONLY` 23 条、`TRADE_SIGNAL` 1,210 条、`CONTEXT_ONLY` 8,316 条、`IGNORE` 451 条；交易或风险文档 1,233 条，形成 1,151 个唯一事件事实，重复事件文档 82 条；不可追溯文档、发布时间缺失和角色冲突均为 0。连续执行两次后清洗文档和事件事实数量不增长，幂等验证通过。

V5 的 10,000 条影子集合数据量约 73.04MB，实际存储与索引约 42.74MB；按当前 510,892 条全量线性外推约 2.13GB，比 V3 的 7.59GB 外推下降约 71.9%。基础数据清洗流水线 Gate 已通过，可以进入受控分批回填准备。

基础 Gate 通过不代表模型收益 Gate 通过。固定人工标注集准确率、重大风险召回率和误报率、点时一致性、Rank IC 与扣成本收益仍未完成，因此新闻排名权重继续保持为 `0`，生产全量回填仍需先审查 V5 影子证据和容量策略。
